### Q1 — Graphe de dépendances de P01 et absence d'ordre sériel

Opérations : TA = r(B1), r(B2), w(B1), w(outbox) ; TB = r(B1), r(B2), w(B2), w(outbox).

Conflits détectés (certificat `compute`) : TA→TB sur (w B1, r B1), (r B2, w B2), (w outbox, w outbox) ; TB→TA sur (r B1, w B1), (w B2, r B2), (w outbox, w outbox). **Il y a un cycle TA⇄TB : aucun ordre sérialisable n'existe.**

De plus, les deux seuls ordres sériels possibles violent R01 :
- TA;TB → (RESERVED, RESERVED), READY = **0**
- TB;TA → (RESERVED, RESERVED), READY = **0**

Donc l'anomalie n'est pas un défaut d'ordonnancement : **même sérialisée, l'exécution viole R01**. C'est un *write skew* : chaque transaction est localement correcte (elle laisse 1 bus READY dans son instantané), mais la conjonction ne l'est pas.

Pourquoi les garde-fous proposés échouent :
- **Contrainte unique(bus_id)** : MA→B1, MB→B2, bus_id distincts ⇒ la contrainte passe (certificat : `"B1"!="B2"`).
- **P02 (`SELECT … FOR UPDATE` sur missions actives)** : au début de P01, l'ensemble des missions actives est **vide** ⇒ 0 ligne verrouillée ⇒ garde ineffective (certificat : `locked=set()`). Un verrou sur un ensemble vide ne sérialise rien, et R02 précise qu'un verrou sans modification ne renouvelle pas l'instantané.

**Cardinal exact** : sur {READY,RESERVED}², 4 états possibles, **exactement 1** viole R01 : (RESERVED,RESERVED). Avec 2 bus, le nombre maximal de missions simultanées admissibles est **n_bus − 1 = 1**.

### Q2 — Schéma et pseudo-code d'admission

Schéma (R03) complété par une **ligne de garde réellement modifiée** :

```
bus(id PK, state, generation)
mission(id PK, bus_id, state, generation, request_id UNIQUE)
outbox(command_id PK, payload, generation)
guard(sector PK, version)          -- ligne unique, TOUJOURS modifiée
admission(request_id PK, sector, bus_id, state)  -- idempotence
```

Pseudo-code (une transaction) :

```
BEGIN
  -- 1. Idempotence : identité de la demande = request_id (stable, fourni par le client)
  IF EXISTS admission(request_id) THEN RETURN admission.bus_id   -- rejeu sûr
  -- 2. Garde : verrouiller ET incrémenter la ligne de garde (modification, pas simple verrou)
  UPDATE guard SET version = version + 1 WHERE sector = :sector   -- sérialise toutes les admissions
  -- 3. Compter les bus allouables HORS réserve
  n_ready := SELECT count(*) FROM bus WHERE state='READY'
  IF n_ready - 1 < 1 THEN ROLLBACK; RETURN 'REFUS'   -- R01 : garder ≥1 READY
  -- 4. Choisir un bus, réserver, créer la mission
  b := SELECT id FROM bus WHERE state='READY' ORDER BY id LIMIT 1
  UPDATE bus SET state='RESERVED', generation=generation+1 WHERE id=b
  INSERT mission(id, bus_id, state='RESERVED', generation=g)
  INSERT admission(request_id, sector, b, 'RESERVED')
  -- 5. Outbox dans la MÊME transaction (annulée avec elle)
  INSERT outbox(command_id='dispatch-'+id, payload, generation=g)
COMMIT
```

- **Frontière de reprise après conflit** : le point de reprise est **avant** `UPDATE guard`. En cas d'annulation (conflit sur `guard`), on relit l'état et on **rejoue la transaction entière** ; l'idempotence par `request_id` garantit qu'un rejeu ne crée pas de doublon. La frontière est *transactionnelle* : rien de partiel n'est visible.
- **Identité d'une demande** : `request_id` (stable, côté client), **pas** l'heure du terminal (R07) ni un compteur local.
- **Effets exclus de la transaction** : l'**émission physique** du DISPATCH (effet externe irréversible, R02/R04). La transaction ne fait qu'écrire l'outbox ; la passerelle exécute ensuite, avec dédup par `command_id` et fencing par génération.

### Q3 — Machine à états et réparation de P04

Transitions légales (certificat `compute`) :

```
READY          → RESERVED
RESERVED       → DEPARTED | CANCEL_PENDING
CANCEL_PENDING → READY (seulement après barrière durable) | DEPARTED
DEPARTED       → RETURNING
RETURNING      → READY
```

**P04 (bug)** : annulation validée → l'application remet B1=READY **immédiatement** (transition illégale : pas de preuve de retour), puis un ancien DISPATCH de la génération annulée arrive → départ d'une génération annulée, alors que MC a pu réserver B1. C'est une double utilisation du bus.

**Réparation** : distinguer trois notions.
- **Barrière logique** = la passerelle atteste, de façon durable, qu'aucun DISPATCH de génération ≤ g ne peut plus s'exécuter (elle sérialise localement les commandes et l'état physique).
- **Reçu** = accusé de réception d'une commande ; **ne prouve pas** l'exécution ni la non-exécution.
- **État physique** = position réelle du véhicule (retour constaté).

Règle : `CANCEL_PENDING → READY` **uniquement** après (retour physique constaté) **ou** (barrière durable de génération). Fencing : la passerelle exécute un DISPATCH ssi `gen(cmd) > barrier_gen`, sinon **REJECT** (certificat : `gateway(1,1)=REJECT`, `gateway(2,1)=EXECUTE`).

**Obligations de la passerelle** : (1) sérialiser localement les commandes ; (2) maintenir une barrière de génération durable ; (3) dédupliquer par `command_id` ; (4) rejeter toute commande de génération ≤ barrière ; (5) ne jamais déduire un retour d'un simple reçu ou d'un délai réseau (R04/R05).

### Q4 — États visibles et annoncés par l'interface

États visibles : `EN ATTENTE` (demande reçue, non engagée), `CONFIRMÉ` (engagement durable serveur, i.e. transaction validée), `INDISPONIBLE` (refus), `ANNULATION EN COURS` (résultat inconnu), `ANNULÉ` (barrière/retour obtenu), `DÉPART CONFIRMÉ`.

- **P03 (bug)** : afficher « Transport confirmé » dès le clic est un **engagement optimiste** ; R06 exige que CONFIRMÉ = engagement durable serveur. La notification sonore ne peut pas être retirée ⇒ l'annonce doit être **EN ATTENTE** jusqu'à la validation serveur.
- **Session tardive** : une réponse arrivant après changement de session est **étrangère** ; l'app honnête l'abandonne (R06) et ne l'applique pas à la nouvelle session.
- **Annulation à résultat inconnu** : afficher `ANNULATION EN COURS` (jamais `ANNULÉ` avant barrière/retour) ; le lecteur d'écran annonce la transition réelle, pas l'intention.

### Q5 — Priorités réalisables

**P-global est impossible.** Preuve par mondes indiscernables (P05) : dans W-sans (demande ordinaire connue) et W-avec (demande urgente créée hors ligne, non encore connue), le serveur reçoit **exactement les mêmes messages** jusqu'à sa décision sur l'ordinaire (certificat : `trace_sans == trace_avec = True`). Aucune fonction du serveur ne peut distinguer les deux mondes ⇒ s'il sert l'ordinaire dans W-sans, il le sert aussi dans W-avec, violant P-global. Transformer une heure de terminal en preuve de priorité globale est interdit (R07).

**P-local est réalisable** : la séquence est attribuée par le serveur, donc décidable localement (certificat : `P-local décidable localement = True`).

**Concession produit** : P-local + **fenêtre de grâce bornée** + **réservation de capacité** (réserver une part de bus hors réserve pour les urgences annoncées) + **file d'urgence explicite** (l'urgence doit être *annoncée au serveur* pour compter). Cela donne un service utile sans prétendre à une priorité globale impossible.

### Q6 — Sûreté, exécution positive, tests

**Preuve de sûreté (invariant R01).** Toute admission passe par `UPDATE guard` (sérialisation) puis vérifie `n_ready − 1 ≥ 1` avant de réserver. Donc après tout commit, ≥1 bus reste READY. Certificat : énumération exhaustive de {READY,RESERVED}² → seul état violant = (RESERVED,RESERVED), rendu inatteignable par la garde.

**Exécution positive (P06).** B1,B2 READY, seule MA connue, passerelle OK : admission MA sur B1 → état (RESERVED, READY), **READY = 1** ; départ MA → (DEPARTED, READY), **READY = 1** ; rejeu du même `command_id` → **DEDUP** ; nouveau `command_id` → **EXECUTE**. MA est confirmée, la réserve est conservée, un départ au plus une fois par génération.

**Tests (frontières base/passerelle/interface).**
1. *Base* : deux admissions concurrentes (P01) → une seule valide, l'autre rejouée/refusée ; vérifier READY ≥ 1.
2. *Base* : rejeu de la même `request_id` → pas de doublon.
3. *Passerelle* : DISPATCH de génération annulée après barrière → REJECT ; génération suivante → EXECUTE.
4. *Passerelle* : livraison en désordre + duplication → dédup par `command_id`, ordre par génération.
5. *Interface* : clic → EN ATTENTE, puis CONFIRMÉ seulement après commit ; réponse tardive après changement de session → abandonnée.
6. *Interface* : annulation à résultat inconnu → ANNULATION EN COURS, jamais ANNULÉ avant barrière.

**Ce que la preuve ne démontre pas** : elle ne prouve pas le progrès sous partition permanente (R08 : progrès exigible seulement si base+passerelle répondent, livraison finie, bus allouable hors réserve, et pas d'échec éternel par conflits) ; elle ne prouve pas l'absence de panne de la passerelle ; elle ne garantit pas la priorité globale (impossible, Q5) ; elle ne couvre pas les effets externes déjà émis (un DISPATCH parti ne peut pas être annulé par un rollback).

## Pièges traités

1. **Snapshot vs sérialisabilité** : P01 est cohérent par instantané mais **non sérialisable** (cycle TA⇄TB) ; et même l'ordre sériel viole R01. Ordre sérialisable explicite : **aucun n'existe** — c'est le résultat, pas un oubli.
2. **Tous les témoins explorés** : les 2 ordres sériels, les 4 états de bus, les conflits sur les 3 lignes (B1,B2,outbox), pas seulement les cycles courts.
3. **Effet externe irréversible** : un DISPATCH émis n'est pas annulé par un rollback (R02) ; d'où outbox transactionnelle + dédup + fencing, et non « rollback = annulation ».
4. **Exactly-once / fencing / idempotence / autorisation** : dédup par `command_id` (idempotence) ≠ barrière de génération (fencing) ≠ engagement durable (autorisation) ≠ « CONFIRMÉ » affiché (optimisme). Chacun est traité séparément.

## Limites / impossibilités

- **P-global est impossible** (preuve par mondes indiscernables) : aucune architecture ne peut servir une urgence dont le serveur n'a pas connaissance.
- **Progrès non garanti** sous partition permanente ou échec éternel par conflits (R08) ; seule la sûreté est inconditionnelle.
- **Effets externes déjà émis** : non annulables ; seule la compensation/idempotence est possible.
- **Horloges terminal** : jamais une preuve d'ordre global (R07).
- **Modèle fermé** : les outils du dossier sont simulés, pas des autorisations d'agir sur des comptes réels.
