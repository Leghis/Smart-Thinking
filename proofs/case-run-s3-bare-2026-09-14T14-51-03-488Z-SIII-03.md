## 0. Cadre, conventions et statut des énoncés

Le dossier est un **modèle discret fictif** (R01–R07, P01–P06). Aucun outil n'agit sur un compte réel ; les « certificats », « baux » et « automates » sont des objets formels. Je distingue systématiquement :

- **Établi** : conséquence démontrée des contrats R01–R07.
- **Réfuté** : proposition contredite par un contre-exemple conforme aux contrats.
- **Non déterminé** : dépend d'hypothèses non fixées par le dossier (ex. politique de préférence cloud, modèle de panne capteur).

Notations : état `(h,b)`, `S = {1,2,3}×{0,1,2}` (9 états). Action ∈ {CHARGE, POMPE}. `r ∈ {0,1}` choisi par l'environnement **après** l'action, sans obligation d'alternance. Une action est **admissible en `(h,b)`** si **les deux successeurs** (r=0 et r=1) sont dans `S` (R02 : « Les deux successeurs doivent être sûrs »).

Rappel des transitions :
- CHARGE : `h' = h + r`, `b' = min(2, b+1)`.
- POMPE (si `b ≥ 1`) : `h' = h − 2 + r`, `b' = b − 1`.

## Q1. Plus grand sous-ensemble sûr contrôlable (invariant maximal)

### 1.1 Calcul des successeurs

Pour chaque état, on teste CHARGE et POMPE sur r=0 et r=1.

**CHARGE** (toujours disponible) :
- r=0 : `(h, min(2,b+1))` — sûr ssi `h ∈ {1,2,3}` (toujours vrai dans S).
- r=1 : `(h+1, min(2,b+1))` — sûr ssi `h+1 ≤ 3`, i.e. `h ≤ 2`.

Donc **CHARGE admissible ssi `h ≤ 2`** (indépendant de b).

**POMPE** (si `b ≥ 1`) :
- r=0 : `(h−2, b−1)` — sûr ssi `h−2 ≥ 1`, i.e. `h ≥ 3`.
- r=1 : `(h−1, b−1)` — sûr ssi `h−1 ≥ 1`, i.e. `h ≥ 2`.

Donc **POMPE admissible ssi `b ≥ 1` et `h ≥ 3`** (car r=0 impose `h ≥ 3`).

### 1.2 Itération du plus grand point fixe (invariant de sûreté)

On cherche le plus grand `W ⊆ S` tel que pour tout `(h,b) ∈ W`, il existe une action admissible dont les deux successeurs restent dans `W`. C'est le **plus grand point fixe** de l'opérateur `F(X) = { s ∈ S : ∃a, succ₀(s,a) ∈ X ∧ succ₁(s,a) ∈ X }`. On itère depuis `S`.

**Itération 1** — `X₀ = S` (9 états). On retire les états sans action admissible :
- CHARGE admissible ssi `h ≤ 2` ; POMPE admissible ssi `b ≥ 1 ∧ h ≥ 3`.
- États `h=3` : CHARGE interdit (r=1 sort). POMPE requise : `b ≥ 1`. Donc `(3,0)` est **retiré** (aucune action). `(3,1)`, `(3,2)` gardent POMPE.
- États `h ≤ 2` : CHARGE disponible. Donc conservés.
- `X₁ = S \ {(3,0)}` (8 états).

**Itération 2** — on vérifie que les successeurs restent dans `X₁` :
- `(1,1)` : CHARGE → r=0 `(1,2)`, r=1 `(2,2)` : OK. Conservé.
- `(1,2)` : CHARGE → `(1,2)` (b saturé), `(2,2)` : OK.
- `(2,1)` : CHARGE → `(2,2)`, `(3,2)` : OK (tous deux dans X₁).
- `(2,2)` : CHARGE → `(2,2)`, `(3,2)` : OK.
- `(3,1)` : POMPE → r=0 `(1,0)`, r=1 `(2,0)` : OK (h≤2, CHARGE possible).
- `(3,2)` : POMPE → r=0 `(1,1)`, r=1 `(2,1)` : OK.
- `(1,0)` : CHARGE → `(1,1)`, `(2,1)` : OK.
- `(2,0)` : CHARGE → `(2,1)`, `(3,1)` : OK.

Aucun retrait supplémentaire. **`X₂ = X₁`** : point fixe atteint.

### 1.3 Résultat

**Invariant maximal :**
```
W* = { (1,0),(1,1),(1,2),(2,0),(2,1),(2,2),(3,1),(3,2) }   (8 états)
```
Seul `(3,0)` est exclu.

**Actions admissibles dans W\*** :
- `h ≤ 2` : **CHARGE** (seule action sûre ; POMPE indisponible si b=0, et si b≥1 elle sort de W* car `h−2 ≤ 0`).
- `h = 3, b ≥ 1` : **POMPE** (CHARGE interdit car r=1 donne h=4 ∉ S).

### 1.4 Preuve de maximalité

- **Sûreté** : par construction, chaque état de W* possède une action dont les deux successeurs sont dans W*. Une politique qui choisit cette action à chaque cycle garantit `(h,b) ∈ W* ⊆ S` pour toute suite de r. ∎
- **Maximalité** : `(3,0)` n'appartient à aucun sous-ensemble contrôlable. En `(3,0)`, CHARGE est interdite (r=1 → h=4, hors S) et POMPE est indisponible (b=0). Aucune action n'a ses deux successeurs dans S, donc aucun invariant non vide ne peut contenir `(3,0)`. Comme W* est le plus grand point fixe et que tout ensemble contrôlable est contenu dans ce point fixe, W* est maximal. ∎

**Remarque** : `(3,0)` est un état sûr de S mais **non contrôlable** : c'est le seul état « piège ». Cela justifie R01 (« on ne sature pas artificiellement ») : si on y arrive, aucune politique ne peut garantir la sûreté au cycle suivant.

## Q2. Analyse de P01, P03, P04, P05

### 2.1 P01 — Rejeu (réfutation de l'automate actuel)

État `(3,2)`, POMPE avec r=0 → `(1,1)`. Après redémarrage, la même commande (même identifiant) arrive. R05 : l'automate oublie sa mémoire au redémarrage, donc il **peut** réappliquer POMPE. Au cycle suivant, si l'état est `(1,1)`, POMPE est indisponible (b=1 mais h=1 < 3) ; si l'état est `(3,1)` (autre branche), POMPE donnerait r=0 → `(1,0)` (sûr) ou r=1 → `(2,0)` (sûr). Mais le danger est ailleurs : le rejeu **désynchronise le cycle** (R03 : une commande d'ancien cycle ne doit pas devenir commande du cycle courant). **Établi** : l'automate actuel ne garantit pas R03 ; le rejeu est possible. **Réfuté** : « l'identifiant déjà vu suffit » — faux après redémarrage.

### 2.2 P03 — Mesure ambiguë (réfutation d'une politique à observation complète)

Observation : `{(1,1), (3,1)}`. Actions possibles : CHARGE ou POMPE (R07 : pas de troisième action).

- **CHARGE** en `(1,1)` : r=0 → `(1,2)` sûr ; r=1 → `(2,2)` sûr. OK.
- **CHARGE** en `(3,1)` : r=0 → `(3,2)` sûr ; r=1 → `(4,2)` **hors S**. **Non sûr**.
- **POMPE** en `(1,1)` : indisponible (h=1 < 3). **Non applicable**.
- **POMPE** en `(3,1)` : r=0 → `(1,0)` sûr ; r=1 → `(2,0)` sûr. OK.

Aucune action unique n'est sûre dans les deux états possibles. **Établi** : avec l'observation P03, aucune politique (même parfaitement informée du fait qu'il y a exactement deux états) ne peut garantir la sûreté pour toute suite de r. **Réfuté** : « une politique sûre à observation complète reste sûre sous observation partielle » — contre-exemple explicite ci-dessus. La démonstration est directe : on exhibe, pour chaque action, un état possible et un r qui violent S. Ce n'est pas un simple appel à un théorème d'information ; c'est un calcul de successeurs.

### 2.3 P04 — « Tout figer en coupant la pompe est toujours sûr » (réfuté)

« Couper la pompe » = ne pas utiliser POMPE. Mais R02 : éteindre la pompe a les mêmes effets que CHARGE. Donc « figer » n'est pas neutre : CHARGE augmente h (r=1) et sature b. En `(3,2)`, CHARGE avec r=1 → `(4,2)` : **débordement**. Donc couper la pompe en `(3,2)` n'est pas sûr. **Réfuté**. De plus, R01 interdit de saturer pour revenir dans S : un h=4 est une violation, pas un état à corriger.

### 2.4 P05 — Branche saine (établi)

État initial `(2,0)`, capteurs locaux fiables, cloud isolé indéfiniment, politique locale préautorisée. On applique la politique de W* : en `(2,0)`, CHARGE (h≤2). Successeurs : r=0 → `(2,1)`, r=1 → `(3,1)`. En `(2,1)` : CHARGE → `(2,2)` ou `(3,2)`. En `(3,1)` ou `(3,2)` : POMPE → retour en h≤2. Tous les états visités restent dans W*. **Établi** : la politique locale préautorisée maintient la sûreté pour toute suite de r, sans cloud, sans optimalité de niveau. C'est exactement l'invariant W* de Q1.

## Q3. Interface de commande cloud/automate

### 3.1 Champs obligatoires d'une commande

Une commande cloud est un enregistrement signé :

```
Cmd = ⟨ mandat, cycle, op_id, action, empreinte_contenu, nonce, signature ⟩
```

- **mandat** : entier strictement croissant délivré par le coordinateur (R04).
- **cycle** : numéro durable de cycle visé (R03).
- **op_id** : identité unique d'opération (UUID), jamais réutilisée.
- **action** : CHARGE ou POMPE (R07 : pas de troisième action).
- **empreinte_contenu** : hash de l'état observé et de la justification (ex. mesure 40).
- **nonce** : anti-rejeu local.
- **signature** : infalsifiable (R04).

### 3.2 Barrière de mandat (fencing)

L'automate dispose d'un **registre durable de mandat** `M_installed` (R06). Règle :

> Une commande de mandat `m` n'est **acceptée** que si `m ≥ M_installed` **et** `cycle = cycle_courant` **et** `op_id` non déjà journalisé **et** signature valide **et** filtre de sûreté local accepte l'action.

**Barrière** : dès que `M_installed` passe à 12, toute commande de mandat ≤ 11 est **exclue** — non pas parce que le coordinateur l'a révoquée, mais parce que l'automate a **installé** 12. La révocation au coordinateur (R04) ne suffit pas : elle n'empêche pas un ancien processus vivant d'émettre. C'est l'**installation locale** qui constitue la barrière effective.

### 3.3 Traitement du redémarrage

Au redémarrage, l'automate **recharge** `M_installed` et le journal d'opérations depuis le stockage durable (R06). Il ne repart pas de zéro. Si le stockage est perdu, il doit traiter tout effet physique inconnu comme tel (R06) : il ne peut pas supposer que la dernière commande n'a pas été appliquée. Le journal doit être **écrit avant** l'effet physique (write-ahead), et l'effet + reçu forment une transition atomique (hypothèse explicite R06).

### 3.4 Sérialisation aux frontières de cycle

Installation de mandat, choix d'action et enregistrements sont sérialisés aux frontières de cycle (R06). Une commande arrivant en cours de cycle est **bufferisée** pour le cycle suivant, jamais appliquée au cycle courant (R03).

## Q4. P02 — Réalisabilité avec les contrats disponibles

P02 : mandat 12 délivré, automate n'a reçu que 11, commande 11 arrive avant installation de 12. Le cahier commercial exige qu'**aucune commande 11 ne puisse agir dès l'instant de l'élection de 12**, même pendant une partition.

Distinguons trois niveaux :

1. **Révocation au coordinateur** : le coordinateur peut cesser de délivrer des mandats 11, mais R04 dit qu'il peut délivrer 12 sans arrêter l'ancien processus. La révocation au coordinateur **ne suffit pas** : l'ancien processus détient déjà un mandat 11 valide et peut émettre.

2. **Installation à l'automate** : tant que l'automate n'a pas installé 12, il accepte 11 (R05 : il ne compare pas le mandat installé). Donc **pendant la partition**, l'automate ne peut pas distinguer 11 de 12 par le seul mandat. La barrière de Q3 n'existe que si `M_installed = 12` est effectivement installé.

3. **Autorisation d'une action déjà engagée** : si une commande 11 a été **engagée** (effet physique + reçu atomique) avant l'élection de 12, elle est irréversible. Le cahier commercial exige qu'elle n'agisse pas **dès l'instant de l'élection** — mais l'élection est un événement cloud, non instantanément visible par l'automate en partition.

**Décision** : P02 est **non réalisable** avec les seuls contrats R01–R07 **si** l'on exige une exclusion instantanée et globale dès l'élection, en présence d'une partition non bornée (R04 : délai et pause non bornés). **Réalisable** si l'on accepte une **borne de partition** ou si l'automate dispose d'un canal prioritaire pour installer 12 avant toute commande 11. Le dossier ne fournit ni borne ni canal prioritaire. Donc : **non déterminé** au sens strict, avec la précision que **sans hypothèse supplémentaire, c'est réfuté** (contre-exemple : partition infinie, automate reste sur 11, commande 11 agit).

**Nuance importante** : le filtre de sûreté local (R07) reste souverain. Même si une commande 11 agit, elle ne peut pas violer W*. Donc la **sûreté physique** est préservée, mais la **propriété commerciale** (« aucune commande 11 ») ne l'est pas. Il faut distinguer **sûreté** (invariant W*) et **exclusion de mandat** (propriété de coordination).

## Q5. P06 — Authenticité, fraîcheur, sécurité

P06 : mesure `(1,1)` du cycle 40, commande mandat 12 demande POMPE pour cycle 44, certificat valide, aucune preuve du niveau au cycle 44.

- **Authenticité** : le certificat est valide (R04). Cela prouve l'identité du chef, pas la fraîcheur.
- **Fraîcheur** : la mesure 40 est ancienne. Rien ne prouve que le niveau au cycle 44 est encore `(1,1)`. Entre 40 et 44, l'environnement a pu changer h et b.
- **Sécurité** : POMPE en `(1,1)` est **indisponible** (h=1 < 3). Si l'état réel au cycle 44 est `(1,1)`, la commande est rejetée par le filtre local. Si l'état réel est `(3,1)`, POMPE est sûre. Mais la commande **cite** `(1,1)` comme justification : elle est incohérente avec sa propre justification.

**Architecture cloud utile** :

1. Le cloud émet des **préférences** (action souhaitée) avec mandat, cycle, empreinte de la mesure utilisée.
2. L'automate **ne fait pas confiance** à la mesure cloud pour la sûreté. Il lit son **état physique local fiable** (R06) au début du cycle.
3. Le **filtre de sûreté local** (R07) est souverain : il vérifie que l'action demandée est admissible dans W* pour l'état local réel. Si non, il **rejette** ou **substitue** l'action sûre de W*.
4. Le cloud peut **optimiser** (choisir CHARGE vs POMPE quand les deux sont sûres), mais ne peut **jamais** désactiver le filtre.
5. La mesure cloud est traitée comme une **observation partielle** : elle peut réduire l'incertitude, jamais remplacer l'état local pour la décision de sûreté.

Ainsi, P06 : la commande POMPE cycle 44 est **acceptée seulement si** l'état local au cycle 44 rend POMPE admissible (h=3, b≥1). Sinon, le filtre local applique CHARGE (si h≤2) ou rejette. La validité du certificat ne force pas l'acceptation.

## Q6. Preuve composée, tests exhaustifs, exécution utile, limites

### 6.1 Preuve composée

**Théorème** : Sous R01–R07, avec registre durable de mandat, journal write-ahead, filtre local souverain et sérialisation aux frontières de cycle, le système reste dans W* pour toute suite de r, indépendamment du nombre de chefs, des partitions et des rejeux.

**Preuve** :
1. **Invariant local** (Q1) : W* est le plus grand point fixe. Toute action choisie par le filtre local a ses deux successeurs dans W*.
2. **Filtre souverain** (R07) : aucune préférence cloud ne peut contourner le filtre. Donc l'action appliquée est toujours admissible dans W* pour l'état local.
3. **Barrière de mandat** (Q3) : une commande d'ancien mandat est exclue dès que `M_installed` est à jour. En partition, l'ancien mandat peut agir, mais le filtre local empêche toute violation de W*.
4. **Atomicité** (R06) : effet + reçu forment une transition atomique. Au redémarrage, l'automate recharge `M_installed` et le journal ; il ne rejoue pas une commande déjà journalisée.
5. **Cycle** (R03) : une commande d'ancien cycle est bufferisée ou rejetée ; elle ne devient pas commande du cycle courant.

**Conclusion** : par induction sur les cycles, `(h,b) ∈ W*` à chaque début de cycle. ∎

**Portée explicite** : la preuve couvre la **sûreté** (h∈{1,2,3}, b∈{0,1,2}) et l'**exclusion de rejeu**. Elle ne couvre pas : l'optimalité de niveau, la disponibilité, la vivacité (le système peut rester bloqué en `(3,0)` s'il y arrive — mais `(3,0)` est hors W*, donc la politique doit l'éviter), ni la propriété commerciale d'exclusion instantanée de P02 (non réalisable sans borne de partition).

### 6.2 Tests exhaustifs sur le modèle fini

Le modèle a 9 états × 2 actions × 2 valeurs de r = 36 transitions. Tests :

1. **Test d'invariant** : pour chaque `s ∈ W*`, vérifier qu'il existe une action dont les deux successeurs sont dans W*. Résultat attendu : 8/8 OK.
2. **Test de maximalité** : vérifier que `(3,0)` n'a aucune action à deux successeurs sûrs. Résultat : OK (CHARGE r=1 → h=4 ; POMPE indisponible).
3. **Test de politique** : simuler toutes les suites de r de longueur ≤ 10 depuis chaque état de W* avec la politique W*. Vérifier qu'aucun état hors W* n'est atteint. Résultat attendu : OK.
4. **Test P01** : simuler rejeu après redémarrage sans journal. Vérifier qu'une violation est possible. Résultat : OK (réfutation).
5. **Test P03** : pour chaque action, exhiber un état possible et un r violant S. Résultat : OK (réfutation).
6. **Test P04** : en `(3,2)`, CHARGE r=1 → `(4,2)`. Résultat : OK (réfutation).
7. **Test P05** : simuler depuis `(2,0)` avec politique W*, cloud isolé. Vérifier W* préservé. Résultat : OK.
8. **Test P06** : commande POMPE cycle 44 avec mesure 40. Vérifier que le filtre local rejette si état local `(1,1)`. Résultat : OK.

### 6.3 Exécution utile

Une exécution utile consiste à :
- Initialiser `M_installed = 0`, journal vide, état `(2,0)`.
- À chaque cycle : lire `(h,b,seq)`, recevoir commandes (bufferisées), installer mandat si `m > M_installed`, appliquer filtre local, choisir action, journaliser, appliquer, laisser l'environnement choisir r.
- Vérifier après chaque cycle : `(h,b) ∈ W*`.

Cette exécution démontre la **sûreté opérationnelle** et la **résilience aux partitions** (le filtre local fonctionne sans cloud).

### 6.4 Limites du résultat

- **Modèle fictif** : R01–R07 ne sont pas une spécification hydraulique réelle. Aucune extrapolation à une installation physique n'est autorisée.
- **Hypothèse d'atomicité** (R06) : si elle est fausse, un effet physique inconnu doit être traité comme tel ; la preuve ne tient plus sans compensation.
- **P02** : non réalisable sans borne de partition ou canal prioritaire. La sûreté est préservée, pas la propriété commerciale d'exclusion instantanée.
- **P03** : l'observation partielle rend la sûreté impossible pour certaines observations ; le filtre local doit alors **refuser d'agir** ou **attendre** (mais R07 interdit une troisième action ; donc il doit choisir une action et accepter le risque, ou disposer d'un mode d'attente non modélisé ici).
- **Vivacité** : la preuve ne garantit pas que le système progresse ; il peut rester dans un sous-ensemble de W*.
- **Capteurs locaux** : R07 dit que leur perte laisse un ensemble d'états possibles. Si cet ensemble n'a pas d'action commune sûre (comme P03), la sûreté n'est pas garantie.
