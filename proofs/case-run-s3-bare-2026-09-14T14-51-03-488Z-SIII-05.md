# Résolution : un binaire attesté, une migration irréversible

## Cadre, invariants et statut épistémique

**Invariants du dossier (établis par les contrats R01–R08) :**

- **I1 (identité par digest).** Un artefact est identifié par son digest de contenu ; un tag ou un nom de fichier n'est pas une identité (R01, R02).
- **I2 (provenance ≠ vérité).** Vérifier une signature prouve *qui* a signé *quel contenu exact*, pas la véracité de toute affirmation du signataire (R01).
- **I3 (promotion liée).** L'admission exige : provenance désignée, source s7, verrou l9, recette r4, constructeur FAB, cible x64, manifeste complet, approbation liant digest d'artefact + digest de suite de tests + plan de migration (R02).
- **I4 (tests bornés).** H réussie est une preuve *partielle* ; elle n'exclut pas tout défaut (R03).
- **I5 (reproductibilité stricte).** Bit à bit exige l'égalité de *tous* les octets, métadonnées incluses ; l'égalité ou la différence d'horodatage ne décide pas de l'équivalence comportementale (R03).
- **I6 (trois profils réels).** O, T, X existent et ne sont pas fusionnables (R04).
- **I7 (v1 binaire).** `shared=false` ⇒ {O} ; `shared=true` ⇒ {O,T,X}. Pas de troisième valeur (R05, R07).
- **I8 (v2 ternaire).** PRIVATE ⇒ {O} ; TEAM ⇒ {O,T} ; PUBLIC ⇒ {O,T,X} (R06).
- **I9 (irréversibilité des données).** Un rollback de code ne reprend ni les données TEAM créées ni les copies délivrées (R08).
- **I10 (client isolé).** Aucun correctif distant possible ; le fonctionnement hors ligne de v1 est une contrainte dure (R05).

**Statut des affirmations :**
- *Établi* : ce qui découle logiquement des contrats et pièces.
- *Réfuté* : ce qui contredit un contrat ou une pièce.
- *Non déterminé* : ce que le dossier ne permet pas de trancher.

## Q1 — Décision de promotion A→D et traitement de E

### Artefact A — **REFUS**
- **Contradiction** : entrée obtenue par URL mobile pendant la construction, **absente du manifeste** (P01).
- **Preuve manquante** : manifeste complet des entrées (R02). Une entrée téléchargée sans empreinte immuable est interdite.
- **Preuve contradictoire** : le journal de construction contredit la déclaration « toutes entrées déclarées ».
- H réussie ne sauve pas A : I4 (tests bornés) et I3 (manifeste) sont indépendants.

### Artefact B — **REFUS**
- **Contradiction** : plateforme arm64 alors que la cible de diffusion est x64 (P02, R02).
- **Preuve manquante** : attestation FAB pour la cible x64. L'attestation existe mais pour une autre plateforme.
- La correction fonctionnelle (attestation complète) ne compense pas l'inadéquation de cible.

### Artefact C — **REFUS**
- **Contradiction** : la provenance signée désigne **dC0**, le stockage sert **dC** (P03). Noms et tags identiques ne valent pas identité (I1).
- **Preuve manquante** : provenance FAB portant sur **dC** lui-même.
- Les essais réussis de dC0 sont hors sujet : ils portent sur un autre digest.

### Artefact D — **ADMISSIBLE (sous réserve d'approbation effective)**
- Provenance FAB exacte, s7/l9/r4, x64, manifeste complet (P04).
- H liée à dD réussie.
- L'autorité *peut* approuver digest + plan de migration admissible.
- **Réserve explicite** : « rien n'affirme que tous les bugs possibles ont été exclus » (I4). L'admission est conditionnelle à l'approbation effective liant les trois digests (artefact, tests, plan).

### Artefact E — **REFUS de substitution silencieuse**
- **Contradiction** : dE ≠ dD (horodatage d'archive différent) ; l'approbation vise dD, pas dE (P05).
- **Réfuté** : l'affirmation de reproductibilité bit à bit est fausse — un octet diffère (I5).
- **Non déterminé** : l'équivalence *comportementale* de dE et dD n'est pas établie par la seule analyse d'octets (I5). Elle exigerait une preuve propre (tests liés à dE, analyse différentielle), non fournie.
- **Traitement correct** : soit reconstruire pour obtenir exactement dD, soit traiter dE comme un nouvel artefact soumis à promotion complète (provenance, manifeste, tests, approbation).

**Synthèse Q1** : seuls D est admissible, et seulement après approbation liée. A, B, C, E sont refusés pour des preuves distinctes : manifeste incomplet, cible erronée, provenance décalée, identité divergente.

## Q2 — Impossibilité du mapping TEAM → v1

**Théorème (établi).** Aucune fonction f : {PRIVATE, TEAM, PUBLIC} → {false, true} ne préserve simultanément les accès de O, T, X pour TEAM.

**Preuve par cas exhaustifs.** v1 n'a que deux valeurs (I7) :
- Si f(TEAM) = false ⇒ accès {O}. **Perte de T** (T est membre légitime, R06). Contredit l'exigence « ni perte de l'accès légitime de T ».
- Si f(TEAM) = true ⇒ accès {O,T,X}. **Divulgation à X** (X est extérieur, R06). Contredit « ni divulgation à X ».

Les deux seules images possibles échouent. Aucune troisième valeur n'existe (R07 : « aucun booléen ne dispose d'une troisième valeur cachée »). ∎

**Conséquence sur P06.** Les deux équipes revendiquant une « conversion exacte » ont tort :
- TEAM→true : réfuté (divulgation X).
- TEAM→false : réfuté (perte T). Le slogan « false est prudent » est faux : c'est une perte de droit, pas une prudence.

**Le produit peut-il satisfaire toutes ses exigences sans en modifier une ?**
- **Non**, si l'on exige simultanément : (a) visibilité TEAM exacte, (b) fonctionnement inchangé des clients v1 isolés hors ligne, (c) rollback v1 exact sans perte ni divulgation.
- **Preuve** : (a) impose un état à trois valeurs ; (b) impose que v1, qui ne lit que `shared`, rende un accès correct pour TEAM ; or aucun booléen ne le permet (théorème ci-dessus). Donc (a) ∧ (b) est contradictoire dès qu'un document TEAM existe et qu'un client v1 isolé le consulte.
- **Échappatoire contractuelle** : R06 autorise le serveur à *refuser* un ancien client après décision de fin de support — mais « cela change l'exigence de fonctionnement inchangé ». Donc ce n'est pas une satisfaction, c'est une **modification d'exigence**.
- **Conclusion** : le produit doit **modifier au moins une exigence** : soit abandonner le fonctionnement inchangé de v1 pour les documents TEAM, soit renoncer à TEAM, soit accepter une perte/divulgation. Le dossier ne tranche pas laquelle ; c'est une décision produit, pas une déduction.

## Q3 — Migration par phases et point de non-retour

### Phases

**Phase 0 — Préparation (réversible).**
- Geler les écritures TEAM (R07).
- Déployer le schéma additif : ajouter `visibility`, **conserver `shared`** (R07).
- Déployer un lecteur v2 comprenant les deux formats (R07).
- Aucune donnée TEAM créée. Rollback v1 exact possible.

**Phase 1 — Expansion (réversible).**
- Backfill contrôlé par version de ligne (R07) : convertir les lignes v1 vers un état v2 cohérent, en préservant la sémantique v1 (`shared=false`→PRIVATE, `shared=true`→PUBLIC).
- **Interdit** : convertir vers TEAM (aucune ligne v1 ne peut exprimer TEAM sans perte/divulgation, Q2).
- Validation : chaque ligne convertie doit préserver exactement les accès O/T/X d'origine.
- Rollback v1 exact encore possible : `shared` est intact et cohérent.

**Phase 2 — Compatibilité des lecteurs (réversible).**
- Tous les lecteurs actifs comprennent v2 et v1.
- Les clients v1 isolés continuent de lire `shared` ; pour les documents non-TEAM, le comportement est inchangé.
- Rollback v1 exact encore possible.

**Phase 3 — Écritures TEAM (point de bascule).**
- Autoriser la création de documents TEAM.
- **Dès la première écriture TEAM persistée**, le rollback v1 exact devient impossible : v1 ne peut représenter TEAM sans perte ou divulgation (Q2), et R08 interdit de prétendre reprendre les données.
- **Point de non-retour exact = la première validation (commit) d'une écriture `visibility=TEAM`.**

**Phase 4 — Backfill concurrent (protégé).**
- Backfill avec contrôle de version de ligne (R07) : lire version, écrire conditionnellement sur version inchangée ; sinon abandon/retry.
- Corrige P07 (voir Q6).

**Phase 5 — Validation.**
- Tests de non-régression O/T/X sur les trois visibilités.
- Tests de client v1 isolé sur documents non-TEAM.
- Vérification qu'aucun document TEAM n'est exposé à X.

**Phase 6 — Activation TEAM généralisée.**
- TEAM devient la visibilité par défaut si le produit le décide.
- Rollback v1 déjà impossible pour les documents TEAM.

**Phase 7 — Contraction (irréversible).**
- Supprimer `shared` (R07 le permet, mais c'est destructif).
- **Après contraction, même le rollback v1 des documents non-TEAM devient impossible** : v1 ne peut plus lire le schéma.
- Point de non-retour *total* = suppression de `shared`.

### Point de non-retour exact pour un rollback v1

- **Rollback v1 exact (code + données) reste possible jusqu'à la Phase 2 incluse.**
- **Il devient impossible dès la première écriture TEAM validée (Phase 3).**
- **Il devient impossible pour tous les documents dès la suppression de `shared` (Phase 7).**

R08 confirme : « Revenir au code v1 ne retire pas les données TEAM déjà créées ni les copies déjà délivrées. » Une compensation applicative restreint un accès futur, elle ne reprend pas un contenu divulgué.

## Q4 — Protocole de promotion liant artefact, tests, données, configuration, approbation

### Protocole

1. **Identité** : calculer le digest de l'artefact (dD). Refuser tout tag/nom comme identité (I1).
2. **Provenance** : vérifier la signature FAB sur (digest, s7, l9, r4, x64, manifeste complet). Refuser si une entrée manque (A) ou si la cible diffère (B) ou si le digest signé diffère (C).
3. **Tests** : exécuter H sur le digest exact ; calculer le digest de la suite de tests et de ses résultats. Ne pas extrapoler (I4).
4. **Données** : produire un plan de migration admissible, avec son digest. Le plan doit inclure les phases Q3 et le point de non-retour.
5. **Configuration** : lier la configuration de déploiement (cible x64, feature flags TEAM, gel d'écritures) à son digest.
6. **Approbation** : l'autorité signe un enregistrement liant **les quatre digests** : artefact, tests, plan de migration, configuration. Un tag mobile ne vaut pas identité (R02).
7. **Déploiement** : vérifier que le digest déployé = digest approuvé. Toute divergence bloque.

### Mise à jour du plan après approbation

- **Règle** : toute modification du plan de migration invalide l'approbation liée au digest du plan.
- **Procédure** : produire un nouveau digest de plan, re-soumettre à l'autorité, obtenir une nouvelle approbation liant le nouveau plan. L'artefact et les tests peuvent rester valides si inchangés, mais l'enregistrement d'approbation doit être re-signé.
- **Interdit** : substituer silencieusement un plan modifié sous une approbation existante (analogue à la substitution dE sous approbation dD, P05).

## Q5 — Contre-exemples aux slogans

**« Signé donc sûr » — réfuté.**
- Contre-exemple : C. La signature FAB est valide, mais elle porte sur dC0, pas sur dC servi (P03). La signature prouve *qui a signé quoi*, pas que le contenu servi est celui signé (I2).
- Contre-exemple : A. Provenance FAB vérifiée sur dA, mais entrée non déclarée (P01). La signature ne couvre pas la complétude du manifeste.

**« Tests verts donc compatible » — réfuté.**
- Contre-exemple : A. H réussie, mais manifeste incomplet (P01).
- Contre-exemple : C. Essais de dC0 réussis, mais dC servi (P03).
- Contre-exemple : D. H réussie, mais « rien n'affirme que tous les bugs possibles ont été exclus » (P04, I4).
- Contre-exemple : v1 vs v2. H peut être verte sur v2 et ne rien dire de la compatibilité d'un client v1 isolé sur un document TEAM (Q2).

**« Rollback du code donc rollback des données » — réfuté.**
- Contre-exemple : R08. Revenir au code v1 ne retire ni les données TEAM ni les copies délivrées. Une compensation applicative restreint un accès futur, pas un contenu déjà divulgué.
- Contre-exemple : Phase 3. Dès la première écriture TEAM, le rollback v1 exact est impossible même si le code v1 est redéployé.

**« false est une conversion exacte parce qu'elle est prudente » — réfuté.**
- Contre-exemple : TEAM→false prive T de son accès légitime (Q2). Ce n'est pas prudent, c'est une perte de droit.
- Contre-exemple symétrique : TEAM→true divulgue à X. Les deux mappings sont inexacts ; aucun n'est « exact ».

## Q6 — Branche positive de déploiement et tests de migration

### Branche positive

1. **Artefact** : dD, provenance FAB complète, x64, manifeste complet, H liée réussie.
2. **Approbation** : enregistrement signé liant dD + digest H + digest plan + digest config.
3. **Phase 0** : gel TEAM, schéma additif (`visibility` ajouté, `shared` conservé), lecteur v2 double format.
4. **Phase 1** : backfill v1→v2 préservant la sémantique (`false`→PRIVATE, `true`→PUBLIC), jamais TEAM.
5. **Phase 2** : tous lecteurs v2 ; clients v1 isolés fonctionnent sur documents non-TEAM.
6. **Phase 3** : activation TEAM ; point de non-retour franchi à la première écriture TEAM validée.
7. **Phase 4** : backfill concurrent avec contrôle de version de ligne.
8. **Phase 5** : validation O/T/X et client v1 isolé.
9. **Phase 6** : généralisation TEAM.
10. **Phase 7** : contraction (suppression `shared`) — irréversible.

### Tests de migration

**Test P07 — course de backfill.**
- État initial : ligne `shared=false`, version 4.
- Backfill lit version 4.
- Usager passe à PUBLIC, valide version 5.
- Backfill tente d'écrire PRIVATE **sans condition sur la version** → écrase PUBLIC, perte de données.
- **Correction** : backfill écrit conditionnellement `WHERE version = 4`. Si version ≠ 4, abandon/retry. Le test doit vérifier que la ligne reste PUBLIC (version 5) et que le backfill signale un conflit.
- **Assertion** : après course, `visibility=PUBLIC`, `version=5`, aucune écriture PRIVATE appliquée.

**Test client ancien isolé.**
- Client v1, copie locale autonome, hors ligne (R05).
- Document non-TEAM : `shared=false` → O seul ; `shared=true` → O,T,X. Comportement inchangé.
- Document TEAM : le client v1 ne peut pas représenter TEAM correctement (Q2). Le test doit vérifier que **le serveur refuse** le client v1 sur un document TEAM (R06), et que ce refus est **documenté comme changement d'exigence**, pas comme « fonctionnement inchangé ».
- **Assertion** : aucun document TEAM n'est servi à un client v1 avec un accès incorrect (ni perte T, ni divulgation X).

**Test de non-divulgation X.**
- Pour chaque document TEAM, vérifier que X n'a aucun accès (serveur et client v2).
- Pour chaque document PUBLIC, vérifier que X a accès.

**Test de non-perte T.**
- Pour chaque document TEAM, vérifier que T a accès (serveur et client v2).

**Test de rollback.**
- Avant Phase 3 : rollback v1 exact possible, vérifier que `shared` est cohérent.
- Après Phase 3 : vérifier que le rollback v1 est **refusé** pour les documents TEAM, et que la compensation applicative restreint seulement les accès futurs (R08).
