### 3. Snapshot isolation + écritures disjointes : NON suffisant

Chaque transaction voit un instantané cohérent (lit 0) et les écritures sont disjointes : **aucun conflit ww**. Mais SI autorise le **write skew** : le cycle T1→T2→T3→T1 n'a aucune paire en conflit d'écriture. **Cohérence instantanée ≠ sérialisabilité.**

**Horodatages de validation** : en SI, la validation ne teste que les conflits **write-write** (first-committer-wins). Écritures disjointes ⟹ aucune transaction n'est avortée ⟹ le write skew passe inaperçu. **Les horodatages de validation ne réparent pas l'historique** (ils ne contrôlent pas les arêtes rw).

### 4. Impossibilité (contrat 1) — preuve par deux exécutions indiscernables

Contrat 1 : `apply(k,payload)` irréversible, **sans dédup, sans transaction avec la base, sans consultation d'existence**. Worker avec journal local durable ; panne entre deux instructions ; réponse réseau perdue possible.

Considérons deux exécutions :
- **E1** : `apply` **exécuté**, réponse perdue, crash **avant** de journaliser le succès.
- **E2** : `apply` **non exécuté**, crash **avant** l'envoi.

Dans les deux cas, le journal local est **identique** (intention loggée, pas de succès loggé). Le worker doit prendre la **même** décision :
- **Rejouer** → E1 produit un **double effet** (viole exactly-once).
- **Ne pas rejouer** → E2 n'est **jamais exécuté** (viole l'exécution finale).

Aucune décision ne satisfait les deux objectifs ⟹ **impossible**. C'est l'impossibilité d'exactly-once sans dédup/coordination côté récepteur.

### 5. Redesign : outbox transactionnel + idempotence côté récepteur

**Modification des contrats** : le service expose `apply_once(k, payload)` **idempotent par clé** : il maintient un **store durable** des clés déjà appliquées et retourne le résultat mémorisé (dédup). Clé **déterministe liée au contenu** : `k = hash(txid, payload, version)`.

**Protocole** :
1. **Commit atomique** : dans la même transaction locale que la validation, insérer `(k, payload, statut=pending)` dans une table **outbox**.
2. **Relayeur** : lit l'outbox, appelle `apply_once(k, payload)`, puis marque `statut=done`.

**Points de panne couverts** :
- (a) crash **avant commit** → rien persisté, la transaction est rejouée ;
- (b) crash **après commit, avant envoi** → le relayeur reprend et envoie ;
- (c) crash **après envoi, avant marquage done** → le relayeur renvoie ; le service **déduplique par k** → pas de double effet ;
- (d) **réponse perdue** → identique à (c).

La frontière atomique est **le commit local (validation + insertion outbox)** ; l'effet externe est **hors** de cette frontière mais rendu idempotent par `k`. Sous disponibilité finale, le relayeur finit par exécuter l'effet exactement une fois.

### 6. Fencing token vs clé d'idempotence

**Non, un jeton de fencing strictement croissant ne remplace pas une clé d'idempotence.**

**Contre-exemple** : worker W détient le jeton 5, envoie `apply(5, payload)`, la réponse est perdue, W **rejoue** `apply(5, payload)`. Le service accepte (5 ≥ max vu = 5) et **applique deux fois** → double effet. Le fencing bloque l'écriture **périmée** d'un worker **obsolète** (ordre/autorisation), mais pas le **rejeu du même effet** par le même worker.

**Clé sans liaison au contenu insuffisante** : si la clé est un identifiant **régénéré** à chaque tentative, le rejeu produit une clé **différente** → le service ne déduplique pas → double effet. Il faut une clé **déterministe liée au contenu** (même `(txid, payload)` ⟹ même clé) pour que deux tentatives du même effet logique partagent la clé.
