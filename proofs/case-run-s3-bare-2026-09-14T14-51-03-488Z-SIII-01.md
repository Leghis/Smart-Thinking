# Résolution du dossier « Refuge » : deux validations justes, une ville sans secours

## 0. Cadre, conventions et statut des affirmations

Le dossier est un **modèle fermé** : les outils (base à isolation par instantané, outbox, passerelle sérialisante) sont **simulés**. Aucune action n'est menée sur des comptes réels. Je distingue systématiquement :

- **Établi** : conséquence logique des contrats R01–R08 et des pièces P01–P06.
- **Réfuté** : contredit par une pièce ou un contrat.
- **Non déterminé** : dépend d'hypothèses non fournies ; je l'explicite alors.

Notation : `bus(id, state, generation)`, `mission(id, bus_id, state)`, `outbox(command_id, payload)`, `guard(sector, version)`. États de bus : `READY`, `RESERVED`, `DEPARTED`, `CANCEL_PENDING`. États de mission : `PROPOSED`, `RESERVED`, `DISPATCHED`, `CANCEL_PENDING`, `CANCELLED`, `RETURNED`.

## Q1. Graphe de dépendances de P01, absence d'ordre sériel, insuffisance des contraintes uniques et de P02

### 1.1 Graphe des dépendances

P01 décrit deux transactions TA et TB démarrant **avant toute écriture**, lisant chacune `B1=READY` et `B2=READY`, puis écrivant sur des lignes **distinctes** :

- TA : `bus(B1).state = RESERVED`, `mission(MA).state = RESERVED`, `outbox(dispatch-MA)`.
- TB : `bus(B2).state = RESERVED`, `mission(MB).state = RESERVED`, `outbox(dispatch-MB)`.

Graphe (nœuds = opérations, arêtes = dépendances de lecture/écriture) :

```
TA.read(B1=READY) ──► TA.write(B1=RESERVED)
TA.read(B2=READY) ──► TA.write(B1=RESERVED)   [lecture de contrôle du parc]
TB.read(B1=READY) ──► TB.write(B2=RESERVED)
TB.read(B2=READY) ──► TB.write(B2=RESERVED)
TA.write(B1)  ⊥  TB.write(B2)   (lignes distinctes, pas d'arête directe)
```

**Établi** : il n'existe **aucune arête** entre les écritures de TA et TB (lignes distinctes). Le graphe est acyclique et **sérialisable dans les deux ordres** (TA→TB ou TB→TA) du point de vue de l'isolation par instantané (R02). C'est précisément le piège : la sérialisabilité formelle est satisfaite, mais l'invariant métier R01 est violé.

### 1.2 Absence d'ordre sériel compatible avec R01

R01 exige : *après chaque transaction validée, au moins un des deux bus reste READY*. Considérons les deux ordres sériels possibles :

- **TA puis TB** : après TA, B1=RESERVED, B2=READY → OK. Après TB, B1=RESERVED, B2=RESERVED → **0 READY** → violation R01.
- **TB puis TA** : symétrique → violation R01.

**Établi** : aucun ordre sériel des deux transactions ne préserve R01. L'anomalie n'est donc **pas** un problème de sérialisabilité au sens classique, mais un **problème d'invariant multi-lignes non protégé** (write skew). C'est le cœur du dossier.

### 1.3 Pourquoi les contraintes uniques ne suffisent pas

R03 : « une contrainte unique interdit deux missions actives sur un même bus, mais **ne porte pas sur le nombre de bus READY** ». En P01, MA porte sur B1, MB sur B2 : les contraintes uniques passent. **Établi** : la contrainte unique est locale à un bus, elle ne peut pas exprimer « au moins un bus READY dans le secteur ».

### 1.4 Pourquoi P02 ne résout pas

P02 : `SELECT ... FOR UPDATE` sur les **seules missions déjà actives**. Or au début de P01, **aucune mission active n'existe**. Le verrou ne porte donc sur aucune ligne ; il ne crée aucune dépendance entre TA et TB ; il ne modifie pas l'instantané (R02 : « un simple verrou sans modification ne renouvelle pas l'instantané »). **Réfuté** : P02 ne résout pas l'invariant métier. Il faudrait verrouiller ou modifier une **ligne de garde partagée** (le `guard(sector, version)`), ce que P02 ne fait pas.

## Q2. Schéma et pseudo-code d'une admission correcte

### 2.1 Principe : ligne de garde sérialisante

La seule manière de préserver un invariant **multi-lignes** sous isolation par instantané est de forcer une **écriture concurrente sur une ligne commune** à toutes les admissions du secteur : `guard(sector, version)`. Deux transactions qui modifient la même ligne depuis des instantanés concurrents → au moins une annulée (R02). C'est le point de sérialisation.

### 2.2 Schéma

```sql
-- Existant
bus(id PK, state, generation)
mission(id PK, bus_id FK, state, generation)
outbox(command_id PK, payload)
guard(sector PK, version)

-- Ajouts nécessaires
CREATE UNIQUE INDEX ux_mission_active
  ON mission(bus_id) WHERE state IN ('RESERVED','DISPATCHED','CANCEL_PENDING');
-- (déjà implicite en R03, on l'explicite)

-- Table de demande : identité stable, idempotence
demand(id PK, client_token UNIQUE, sector, priority, created_seq, state)
```

**Identité d'une demande** : `demand.id` est un identifiant **serveur** (séquence attribuée par le serveur, cf. R07 P-local). `client_token` est fourni par le client pour l'idempotence de la soumission (rejeu hors ligne). Une demande n'est **pas** identifiée par une heure de terminal (R07).

### 2.3 Pseudo-code transactionnel d'admission

```
PROCEDURE admit(demand_id, sector):
  BEGIN TRANSACTION
    -- 1. Lire la garde et la MODIFIER (point de sérialisation)
    g = SELECT version FROM guard WHERE sector = :sector FOR UPDATE
    UPDATE guard SET version = version + 1 WHERE sector = :sector

    -- 2. Compter les bus allouables (hors réserve)
    ready = SELECT id FROM bus
            WHERE state = 'READY' AND sector = :sector
            ORDER BY id
    IF count(ready) <= 1 THEN
        ROLLBACK   -- refus : la réserve serait consommée
        RETURN REFUSED
    END IF

    -- 3. Choisir un bus (hors réserve : on garde le dernier READY)
    b = ready[0]   -- politique déterministe

    -- 4. Réserver
    UPDATE bus SET state='RESERVED', generation=generation+1
      WHERE id = b AND state='READY'
    IF rowcount = 0 THEN ROLLBACK; RETURN CONFLICT END IF

    INSERT INTO mission(id, bus_id, state, generation)
      VALUES(:demand_id, b, 'RESERVED', gen)

    -- 5. Outbox : commande de départ, idempotente par command_id
    INSERT INTO outbox(command_id, payload)
      VALUES('dispatch-' || :demand_id || '-' || gen,
             {bus:b, mission:demand_id, gen:gen})

    UPDATE demand SET state='RESERVED' WHERE id=:demand_id
  COMMIT
  RETURN CONFIRMED
```

### 2.4 Frontière de reprise après conflit

- **Conflit détecté** = annulation par la base (R02) sur `guard` ou sur `bus`. La transaction est **entièrement annulée**, y compris l'outbox (R02 : « une annulation supprime toutes ses écritures, y compris celles de l'outbox »).
- **Frontière de reprise** : le client (ou un worker) **rejoue la même `demand_id`** avec le même `client_token`. L'idempotence est assurée par `demand.client_token UNIQUE` : si la demande a déjà été confirmée, on renvoie l'état existant sans réécrire.
- **Effets exclus de la transaction** : aucun effet externe (envoi physique, notification) n'est émis **dans** la transaction. L'outbox est le seul canal ; la passerelle consomme l'outbox **après** commit. R02 : « aucun effet externe n'est annulé par ce mécanisme » → il ne faut donc jamais émettre d'effet externe avant commit.

### 2.5 Ce que cela garantit

**Établi** : deux admissions concurrentes dans le même secteur se sérialisent sur `guard`. La seconde voit `version` incrémentée et/ou est annulée ; dans tous les cas, elle relit l'état des bus **après** la première, donc voit `count(ready)` à jour et refuse si la réserve serait consommée. R01 est préservé.

## Q3. Machine à états et réparation de P04

### 3.1 Machine à états

**Bus** :
```
READY ──admit──► RESERVED ──dispatch_ack──► DEPARTED
  ▲                  │                          │
  │                  │ cancel                   │ return_proof
  │                  ▼                          ▼
  └──── return_proof ── CANCEL_PENDING ──► READY
```

**Mission** :
```
PROPOSED ──admit──► RESERVED ──dispatch_ack──► DISPATCHED
                       │                            │
                       │ cancel                     │ return_proof
                       ▼                            ▼
                  CANCEL_PENDING ──barrier──► CANCELLED
                       │
                       └── return_proof ──► RETURNED
```

Règles :
- `RESERVED → READY` **interdit** sans preuve de retour physique **ou** barrière durable de la passerelle (R05).
- `CANCEL_PENDING` n'est **pas** une disponibilité (R01).
- Une mission `CANCELLED` ne peut pas être redispatchée : la génération est close.

### 3.2 Réparation de P04

P04 : MA RESERVED, DISPATCH en transit. L'annulation valide, l'app remet **immédiatement** B1 à READY, puis un ancien DISPATCH arrive. Aucun retour physique. MC peut avoir réservé B1.

**Faute** : l'application a traité une **annulation logique** comme un **retour physique**. R05 : « une demande d'annulation n'est ni un retour du véhicule ni la preuve qu'il n'est jamais parti ».

**Réparation** :
1. L'annulation met la mission en `CANCEL_PENDING` et le bus en `CANCEL_PENDING` — **jamais** READY directement.
2. La passerelle, qui **sérialise localement** les commandes et l'état physique (R05), doit fournir une **barrière durable** : soit elle atteste qu'aucun départ de la génération annulée n'a eu lieu et qu'aucun ne pourra avoir lieu, soit elle constate le retour physique.
3. Tant que la barrière n'est pas reçue, B1 reste `CANCEL_PENDING` → non allouable. MC ne peut donc pas le réserver.
4. Si l'ancien DISPATCH arrive **après** la barrière, la passerelle le **rejette** car la génération est close (elle connaît la barrière). Si l'ancien DISPATCH arrive **avant** la barrière, la passerelle l'exécute ou le met en attente, mais la barrière ne sera émise qu'après résolution → cohérence.

**Distinction exigée** :
- **Barrière logique** : engagement de la passerelle qu'aucun départ de la génération ne peut plus survenir. Suffit pour `CANCEL_PENDING → READY` (R05).
- **Reçu** : accusé de réception d'une commande. **Ne suffit pas** (un reçu ne prouve pas l'absence de départ).
- **État physique** : constat capteur que le véhicule est sur place. Suffit aussi, mais plus coûteux.

### 3.3 Obligations de la passerelle

**Établi** (R05) : la passerelle doit
1. **sérialiser localement** les commandes par bus ;
2. **persister** la génération courante et les barrières ;
3. **rejeter** toute commande d'une génération close ;
4. **émettre** une barrière durable uniquement après avoir établi qu'aucun départ de la génération ne peut plus avoir lieu ;
5. **ne jamais** dédupliquer par `command_id` seul si cela laisse passer un ancien DISPATCH d'une génération close (R04 : la version actuelle « accepte un ancien ordre DISPATCH tant qu'il n'a pas déjà été exécuté » → à corriger : la déduplication doit inclure la génération).

## Q4. États visibles et annoncés par l'interface

### 4.1 États visibles

| État serveur | État affiché | Annonce lecteur d'écran |
|---|---|---|
| `PROPOSED` | « En cours d'examen » | « Demande enregistrée, non confirmée » |
| `RESERVED` | « Confirmé » | « Transport confirmé » |
| `DISPATCHED` | « En route » | « Véhicule en route » |
| `CANCEL_PENDING` | « Annulation en cours » | « Annulation en cours, véhicule non disponible » |
| `CANCELLED` | « Annulé » | « Transport annulé » |
| `RETURNED` | « Terminé » | « Véhicule revenu » |

**Règle R06** : « CONFIRMÉ » = engagement durable du serveur. Une requête locale, un clic, une notification optimiste **ne sont pas** des confirmations. Donc l'interface ne doit afficher « Confirmé » **qu'après** réception de l'état `RESERVED` du serveur.

### 4.2 P03 est réfuté

P03 affiche « Transport confirmé » **dès le clic**, puis remplace silencieusement par « Transport indisponible ». **Réfuté** : (a) le clic n'est pas un engagement durable (R06) ; (b) le remplacement silencieux viole l'annonce lecteur d'écran (R06 : « un lecteur d'écran annonce les changements d'état ») ; (c) la notification sonore initiale ne peut pas être retirée → l'usager a entendu une fausse confirmation.

### 4.3 Changement de session pendant une réponse tardive

R06 : « une application honnête peut abandonner une réponse devenue étrangère à sa session d'affichage ». Donc :
- Chaque requête porte un `session_id` (ou un jeton d'affichage).
- À la réception d'une réponse, si `session_id` ≠ session courante, l'application **ignore** la réponse (ne met pas à jour l'UI) mais **peut** la journaliser.
- L'état serveur reste la vérité ; l'UI se resynchronise par une lecture d'état.

### 4.4 Annulation dont le résultat est inconnu

- L'UI affiche « Annulation en cours » (état `CANCEL_PENDING`), **pas** « Annulé ».
- Tant que la barrière ou le retour physique n'est pas reçu, le bus reste non allouable.
- Si le résultat reste inconnu (partition), l'UI affiche « Annulation en cours — vérification » et **ne promet pas** la libération.
- **Établi** : on ne peut pas afficher « Annulé » sur la seule base d'une requête locale (R05, R06).

## Q5. Priorités et promesses hors ligne

### 5.1 P-local vs P-global

- **P-local** : priorité aux demandes **complètes déjà connues du serveur**, suivant une séquence attribuée par le serveur. **Réalisable** : le serveur connaît la demande, peut la séquencer, et l'ordre est globalement cohérent.
- **P-global** : toute demande urgente créée ailleurs doit être servie avant une demande ordinaire, **même si le serveur n'en a pas encore connaissance**. **Non réalisable** en l'état : le serveur ne peut pas ordonner ce qu'il ne connaît pas (R07 : « il est interdit de transformer une heure de terminal en preuve de priorité globale »).

### 5.2 Preuve par mondes indiscernables (P05)

W-sans : seul un terminal connecté a une demande ordinaire complète.
W-avec : un terminal isolé a créé auparavant une demande urgente.

Le serveur reçoit **exactement les mêmes messages** jusqu'à sa décision sur la demande ordinaire. Aucune capacité de réserve n'a été préattribuée à l'équipe isolée.

**Établi** : le serveur ne peut pas distinguer W-sans de W-avec. Donc toute politique qui, dans W-avec, servirait l'urgente avant l'ordinaire, devrait aussi le faire dans W-sans — mais dans W-sans l'urgente n'existe pas. Inversement, toute politique qui, dans W-sans, sert l'ordinaire, sert aussi l'ordinaire dans W-avec. **Conclusion** : P-global est **impossible** sans information supplémentaire (préattribution de réserve, canal dédié, ou connaissance préalable). C'est une preuve par indistinguabilité.

### 5.3 Concession produit

**Concession** : réserver une **capacité dédiée** (un bus ou une fraction de capacité) aux urgences, préattribuée et connue du serveur. Ainsi :
- P-global devient réalisable **pour la capacité dédiée** : l'urgente est servie avant l'ordinaire sur cette capacité.
- L'ordinaire utilise la capacité restante.
- Si aucune urgence n'arrive, la capacité dédiée peut être libérée après un délai (mais alors P-global n'est plus garanti pour les urgences tardives).

**Établi** : sans préattribution, P-global est réfuté par P05. Avec préattribution, il est réalisable **dans la limite de la capacité dédiée**. C'est la seule concession compatible avec R07 et R08.

### 5.4 Promesses hors ligne

- **Réalisable** : « Votre demande est enregistrée localement et sera soumise » (pas « confirmée »).
- **Réalisable** : « Vous serez notifié de la décision » (si le canal de notification est fiable).
- **Non réalisable** : « Votre transport est confirmé » hors ligne (R06).
- **Non réalisable** : « Vous serez servi avant les demandes ordinaires » sans préattribution (P05).

## Q6. Preuve de sûreté, exécution positive, tests

### 6.1 Preuve de sûreté

**Théorème** : sous R01–R08 et le protocole Q2–Q3, après chaque transaction validée, au moins un bus du secteur reste READY.

**Preuve** :
1. Toute admission modifie `guard(sector, version)` (Q2, étape 1). Deux admissions concurrentes du même secteur modifient la même ligne depuis des instantanés concurrents → au moins une est annulée (R02).
2. L'admission qui valide lit `count(ready)` **après** avoir acquis la garde (étape 2). Elle refuse si `count(ready) <= 1`.
3. Donc après validation, `count(ready) >= 1` (la réserve est préservée).
4. Les annulations ne remettent un bus à READY qu'après barrière ou retour physique (Q3), donc ne créent pas de fenêtre où `count(ready)` serait faussement augmenté.
5. Les retours physiques augmentent `count(ready)` ; ils ne peuvent pas le diminuer.
6. Par induction sur les transactions, l'invariant tient.

**Ce que la preuve ne démontre pas** :
- Elle ne démontre **pas** le progrès (R08) : sous partitions permanentes, les admissions peuvent échouer indéfiniment. Le progrès n'est exigible que sous les hypothèses de R08 (base et passerelle répondent, échanges livrés, bus allouable en plus de la réserve, pas d'échec éternel par concurrence).
- Elle ne démontre **pas** l'absence de famine entre demandes de même priorité (non spécifié).
- Elle ne démontre **pas** la correction de la passerelle elle-même (supposée sérialisante et durable, R05).
- Elle ne démontre **pas** que P-global est satisfait (réfuté en Q5).
- Elle ne démontre **pas** la terminaison des annulations en cas de panne permanente de la passerelle (le bus reste CANCEL_PENDING, ce qui est sûr mais non progressif).

### 6.2 Exécution positive (P06)

B1, B2 READY ; seule MA connue ; passerelle OK ; pas d'annulation.

1. `admit(MA, secteur)` : garde incrémentée, `count(ready)=2 > 1`, B1 réservé, mission MA RESERVED, outbox `dispatch-MA-gen1`. Commit.
2. Passerelle consomme `dispatch-MA-gen1`, exécute le départ, émet `dispatch_ack`. Bus B1 → DEPARTED, mission MA → DISPATCHED.
3. B2 reste READY → réserve conservée.
4. Le départ a lieu **au plus une fois** : la passerelle déduplique par `(command_id, generation)` ; un rejeu de `dispatch-MA-gen1` est ignoré.

**Établi** : P06 est satisfait.

### 6.3 Tests

**Frontière base** :
- T1 : deux `admit` concurrents même secteur, 2 bus READY → exactement une réussit, l'autre est refusée ou annulée ; `count(ready) >= 1` après.
- T2 : deux `admit` concurrents même secteur, 1 bus READY → les deux refusent (réserve préservée).
- T3 : rejeu de `admit` avec même `client_token` → idempotent, pas de double réservation.
- T4 : annulation concurrente d'une admission → cohérence guard/bus/mission.

**Frontière passerelle** :
- T5 : DISPATCH en transit, annulation, puis ancien DISPATCH arrive → la passerelle rejette (génération close) ; bus reste CANCEL_PENDING jusqu'à barrière.
- T6 : barrière émise, puis rejeu DISPATCH → rejeté.
- T7 : rejeu DISPATCH même génération → exécuté au plus une fois.
- T8 : panne passerelle pendant CANCEL_PENDING → bus non allouable, pas de faux READY.

**Frontière interface** :
- T9 : clic hors ligne → affichage « enregistré », pas « confirmé ».
- T10 : réponse tardive après changement de session → ignorée par l'UI.
- T11 : annulation résultat inconnu → affichage « en cours », pas « annulé ».
- T12 : lecteur d'écran annonce chaque transition d'état, y compris les corrections.

**Frontière priorité** :
- T13 : W-sans vs W-avec avec mêmes messages → même décision (preuve P05).
- T14 : avec préattribution, urgence servie avant ordinaire sur la capacité dédiée.

## Conclusion

L'anomalie de P01 n'est pas un défaut de sérialisabilité mais un **invariant multi-lignes non protégé** : deux transactions sur des lignes distinctes valident alors que leur combinaison viole R01. La correction exige une **ligne de garde effectivement modifiée** (`guard(sector, version)`), pas un verrou sur des missions inexistantes (P02 réfuté). La machine à états doit distinguer **barrière logique**, **reçu** et **état physique** (P04 réparé). L'interface ne doit jamais confondre clic et confirmation (P03 réfuté). P-global est **impossible** sans préattribution (preuve par mondes indiscernables P05) ; la concession est une **capacité dédiée**. La sûreté est démontrée sous R01–R08 ; le progrès ne l'est que sous les hypothèses explicites de R08, et la preuve **ne démontre pas** la correction interne de la passerelle ni l'absence de famine entre priorités égales.
