### Q3 — Snapshot + disjonction des écritures suffisent-ils ?

**Non.** Les écritures sont disjointes (aucun conflit écriture-écriture), et chaque transaction voit un instantané cohérent (l'instantané initial). C'est exactement un **write skew** : les conflits sont des conflits lecture-écriture croisés ($T_1$ lit $b$ écrit par $T_2$ ; $T_2$ lit $c$ écrit par $T_3$ ; $T_3$ lit $a$ écrit par $T_1$), formant le cycle $T_1\to T_2\to T_3\to T_1$. L'isolation par instantané (SI) **autorise** ce cycle car elle ne détecte que les conflits ww. La cohérence instantanée (chaque transaction voit un état cohérent) n'implique pas la sérialisabilité globale.

**Les horodatages de validation ne réparent pas.** Un horodatage de validation ordonne les commits, mais les lectures ont eu lieu sur l'instantané initial : la valeur lue ($0$) est périmée par rapport à l'ordre de validation. Aucun réordonnancement des commits ne peut rendre vraie la lecture de $0$ si l'écrivain est validé avant. Il faudrait une détection de conflit rw (SI étendue / sérialisation par graphe) ou un verrouillage, pas un simple horodatage.

### Q4 — Impossibilité exactly-once + exécution finale (premier contrat)

**Impossible.** Le contrat : `apply(k,payload)` applique un effet **irréversible**, ne déduplique pas, ne participe pas à une transaction avec la base, et ne permet pas de consulter l'existence d'un effet. Le worker a un journal local durable ; une panne peut survenir entre deux instructions ; une réponse réseau peut être perdue.

**Preuve par deux exécutions indiscernables.** Considérons deux exécutions dont l'état local observable du worker est identique (journal sans entrée « commitée ») :

- **Exécution A** : le worker envoie `apply`, le service applique l'effet, mais la **réponse est perdue**, puis le worker tombe en panne avant d'écrire le commit dans son journal.
- **Exécution B** : le worker tombe en panne **avant** d'envoyer `apply` ; aucun effet n'a été appliqué.

Dans les deux cas, le worker redémarre avec le même journal (aucune trace d'effet confirmé). Comme le service n'est **pas consultable** et **non idempotent**, le worker ne peut pas distinguer A de B. Il doit choisir une action unique :

- **Rejouer** `apply` : correct en B (effet appliqué une fois), mais en A l'effet est appliqué **deux fois** → viole *exactly-once*.
- **Ne pas rejouer** : correct en A, mais en B l'effet est **manquant** → viole la *vivacité* (exécution finale).

Aucune action ne satisfait les deux objectifs simultanément : **impossibilité**. (C'est l'argument classique : sans idempotence ni lecture d'état ni atomicité partagée, l'incertitude sur l'issue de l'appel est irréductible.)

### Q5 — Protocole corrigé

**Contrats modifiés :**
1. `apply(idem_key, payload)` devient **idempotent** : le service mémorise durablement `idem_key` et ignore tout doublon (retourne le même accusé).
2. Le service expose `get_status(idem_key)` (consultation d'existence).
3. La clé d'idempotence est **déterministe et liée au contenu** : `idem_key = H(tx_id ‖ registre ‖ valeur ‖ epoch)`.

**Protocole (outbox transactionnel) :**
- **Données persistantes** : table `outbox(idem_key PK, payload, state ∈ {PENDING, SENT, DONE}, epoch)` et table métier, dans **la même base**.
- **Frontière atomique** : la validation de la transaction métier **et** l'insertion de la ligne `outbox` (état `PENDING`) se font dans **une seule transaction locale** (commit atomique). C'est la frontière qui manquait.
- **Envoi** : un relais lit les lignes `PENDING`, appelle `apply(idem_key, payload)`, puis marque `DONE` (transaction locale séparée).
- **Points de panne** :
  - Panne **avant** le commit métier+outbox → rien n'est envoyé (cohérent).
  - Panne **après** commit, **avant** envoi → la ligne `PENDING` survit ; au redémarrage le relais réémet.
  - Panne **après** envoi, **avant** marquage `DONE` → le relais réémet ; l'**idempotence** du service absorbe le doublon.
  - Réponse perdue → même cas : réémission, déduplication par `idem_key`.
- **Vivacité** : tant que la ligne n'est pas `DONE`, le relais réessaie (avec back-off) ; sous disponibilité finale, l'effet finit par être appliqué exactement une fois.

### Q6 — Fencing vs idempotence

**Non, un jeton de fencing strictement croissant ne remplace pas une clé d'idempotence.**

- **Fencing** : le service rejette toute requête dont le jeton est **inférieur** au maximum déjà vu. Il protège contre les **écritures périmées** d'un ancien détenteur (split-brain), mais **accepte** un rejeu portant le **même** jeton.
- **Contre-exemple** : le worker $W_1$ détient l'epoch $5$, envoie `apply(epoch=5)`, le service applique, la **réponse est perdue**, $W_1$ rejoue `apply(epoch=5)`. Le fencing accepte ($5 \ge 5$) → **double effet**. Le fencing ne garantit donc pas l'exactly-once ; seule l'idempotence (mémorisation de la clé) le fait.

**Pourquoi une clé sans liaison au contenu est insuffisante.** Si la clé n'est pas dérivée du contenu (ex. un compteur local, un UUID régénéré à chaque tentative, ou une clé réutilisée), deux situations se produisent :
- **Clé régénérée à chaque rejeu** → le service voit deux clés distinctes pour le même effet logique → **double effet** (l'idempotence ne s'applique pas).
- **Clé réutilisée pour un contenu différent** (collision, renumérotation) → le service déduplique à tort et **supprime un effet légitime** (perte) ou applique le mauvais payload.

Une clé **liée au contenu** (`H(tx_id ‖ registre ‖ valeur ‖ epoch)`) garantit que le même effet logique produit toujours la même clé (déduplication correcte) et que des effets différents produisent des clés différentes (pas de collision sémantique).

## Limites / impossibilités

- **Q4 est une impossibilité stricte** sous le premier contrat : aucune garantie conjointe exactly-once + vivacité n'est possible (preuve par indiscernabilité).
- **Q3** : SI + disjonction des écritures ne peuvent **jamais** garantir la sérialisabilité en présence de write skew ; les horodatages de validation sont insuffisants.
- **Q5** : la garantie exactly-once + vivacité n'est obtenue **que** sous l'hypothèse de **disponibilité finale** (le service et le réseau redeviennent disponibles) et grâce à l'idempotence côté service ; sans cette hypothèse, la vivacité n'est pas garantie (un effet peut rester `PENDING` indéfiniment).
- **Q6** : le fencing seul ne peut pas garantir l'exactly-once ; il faut **conjointement** une clé d'idempotence liée au contenu.
