## Réponse

### Q1 — Interpréteur de référence, traduction SQL, équivalence

**Interpréteur de référence (R01/R03).** Tables de Kleene exactes : `NOT(T)=F, NOT(F)=T, NOT(U)=U` ; `AND` : F domine, sinon U domine T ; `OR` : T domine, sinon U domine F. Prédicat R03 :

```
auth_ref(M,P,R,C,E) = (M AND P AND NOT R AND (C OR E)) IS TRUE
```

**Traduction SQL correcte** (primitives pures R07 uniquement) :

```sql
(M IS TRUE) AND (P IS TRUE) AND (R IS FALSE) AND ((C IS TRUE) OR (E IS TRUE))
```

`IS TRUE`/`IS FALSE` sont les seuls tests explicites autorisés ; ils projettent U→FALSE, ce qui est exactement la sémantique « autoriser seulement si T ».

**Équivalence vérifiée sur les 243 = 3⁵ combinaisons** (énumération exhaustive, comparaison bit à bit) : **0 écart**, les deux autorisent exactement **5** combinaisons :
`(M,P,R)=(T,T,F)` et `(C,E) ∈ {(T,T),(T,F),(T,U),(F,T),(U,T)}`.

**Portée exacte du contrôle fini.** Le contrôle est *exhaustif sur le domaine des valeurs* (les 5 faits × 3 valeurs = 243) : il prouve l'équivalence **extensionnelle** des deux expressions pour toute affectation T/F/U. Il ne prouve **pas** : (a) l'équivalence des *traces* si une primitive a un effet (P04) ; (b) la fraîcheur/cohérence des faits (P05) ; (c) l'atomicité concurrente (P06) ; (d) l'idempotence (P07). C'est une équivalence de *valeur de décision*, pas de *comportement d'exécution*.

### Q2 — Contre-exemples mutants et comptage des autorisations à tort

**P02 — mutant NULL** `... AND NOT COALESCE(R,FALSE) AND ...` : `COALESCE(R,FALSE)` transforme `R=U` en `F`, donc `NOT` donne `T` → autorise alors que R03 exige `R=F` établi.
- **Contre-exemple** : `M=T, P=T, R=U, C=T, E=F` → P02 autorise, R03 refuse (R non établi faux).
- **Autorisations à tort : 5** — exactement `R=U`, `M=P=T`, `(C=T ou E=T)`.

**P03 — mutant de parenthèses** `((M AND P AND NOT R AND C) OR E) IS TRUE` : le `E` est sorti du contexte, donc `E=T` autorise seul, sans M, P ni R.
- **Contre-exemple** : `M=F, P=F, R=T, C=F, E=T` → P03 autorise, R03 refuse.
- **Autorisations à tort : 78** — exactement `E=T` et non(ref). Il y a 3⁴=81 combinaisons avec `E=T`, dont 3 légitimes (M=P=T, R=F, C∈{T,F,U}), donc **81−3 = 78** à tort.

### Q3 — P04 : valeur vs exécution

`OR` est commutatif **sur les valeurs** (`T OR x = T`), mais `consumeEmergencyToken()` a un **effet** (usage unique). Dans P04 (`M=T,P=T,R=F,C=T,E=T`) : l'interpréteur initial évalue `C=T`, court-circuite le `OR` et **ne consomme pas** le jeton ; l'optimiseur place `consumeEmergencyToken()` en premier, renvoie `T` et **consomme** le jeton. La valeur finale est identique (`T`), mais `trace(consume;T) ≠ trace(T)`. R07 : « l'équivalence booléenne de la valeur ne prouve pas l'équivalence de la trace ».

**IR séparant décision et consommation** (deux phases) :
1. **Phase pure** : lire les 5 faits épinglés à une révision, calculer `auth_ref` et `need_token = (C IS NOT TRUE) AND (E IS TRUE)`. Aucun effet, réordonnancement libre.
2. **Phase d'effet** : si `auth_ref=T` et `need_token`, exécuter atomiquement `consume(token)` **dans la même transaction** que l'accès. Si `C=T`, ne jamais appeler `consume` (R04 : accès ordinaire préféré).

### Q4 — Vues de faits, cache, concurrence, linéarisation

- **P05 (révisions croisées)** : e7 dit `R=F`, e8 dit `M=T,P=T`, et à e8 `R=T`. Combiner des signatures de révisions différentes = **mélange de révisions** → chaque fait non couvert par la révision courante vaut **U**, et le mélange est **signalé comme défaut de preuve** (R02). Le frontend ne peut pas affirmer « tous les faits nécessaires sont certifiés » : `R` est périmé.
- **Réparation des vues** : épingler tous les faits à **une seule révision** (snapshot cohérent) ; refuser toute combinaison inter-révisions ; cache de décision indexé par `(révision, principal, organisation, dossier, action, valeurs des 5 faits)`.
- **P06 (concurrence)** : deux requêtes lisent `E=T` avant consommation ; l'usage unique impose qu'**une seule** consomme. **Point de linéarisation** = `UPDATE token SET used=1 WHERE id=? AND used=0` (compare-and-set atomique) exécuté dans la transaction d'accès. La requête perdante voit `E` devenir `U/F` et doit renoncer ou obtenir un nouveau jeton. C'est un cas de *write skew* : un snapshot cohérent par transaction ne suffit pas, il faut le CAS.
- **Politique changeant pendant le calcul** : la décision est prise sur la révision épinglée ; si la révision change avant le commit, la transaction est **abortée et rejouée** (validation optimiste) — jamais de décision hybride.

### Q5 — Idempotence, usage unique, révocation (P07)

- **Rejouer un statut** (opaque, non privé) : idempotent — la clé d'opération garantit qu'un rejeu **ne consomme pas un second jeton** (R05).
- **Divulguer un résultat** : renvoyer l'ancienne projection privée est une **nouvelle divulgation** qui exige une **autorisation de lecture courante** (R06). Après révocation, le cache ne peut pas servir l'ancienne projection : il faut re-vérifier `R` (et les autres faits) à l'instant de la réponse.
- **Réconciliation** : le cache d'idempotence mémorise le *statut* et l'*identifiant d'opération*, pas le *contenu privé*. Le contenu privé n'est libéré qu'après re-autorisation courante. Le cache d'idempotence **n'est pas** une exception générale à la révocation.

### Q6 — Preuve composée, tests, limites

**Preuve composée** (chaîne) :
1. *Équivalence de décision* : `auth_ref ≡ SQL` sur les 243 combinaisons (Q1, exhaustif).
2. *Sûreté des mutants* : P02 sur-autorise 5, P03 sur-autorise 78 (Q2, exhaustif) → mutants rejetés.
3. *Séparation valeur/effet* : la phase pure est réordonnable, la phase d'effet est atomique et conditionnée par `need_token` (Q3).
4. *Cohérence de révision* : faits épinglés à une révision unique ; mélange ⇒ U + défaut de preuve (Q4).
5. *Linéarisation* : CAS atomique sur le jeton = point de linéarisation unique (Q4).
6. *Idempotence vs divulgation* : statut idempotent, projection privée re-autorisée (Q5).

**Tests positifs** : (a) `M=T,P=T,R=F,C=T,E=T` → autorise, **0 jeton consommé** ; (b) `M=T,P=T,R=F,C=F,E=T` → autorise, **1 jeton consommé** ; (c) rejeu de la même opération → **0 jeton supplémentaire** ; (d) `R=F` établi → autorise.

**Tests négatifs** : (a) `R=U` → refuse (P02 doit refuser) ; (b) `E=T` seul sans M/P/R → refuse (P03 doit refuser) ; (c) `C=T,E=T` → ne consomme pas de jeton (P04) ; (d) après révocation, rejeu de A → **refus de divulgation** ; (e) deux requêtes concurrentes sur un jeton → **une seule** réussit.

**Limites frontend/backend** : le frontend ne peut garantir que la *valeur de décision* sur les faits qu'il détient ; il ne peut pas garantir la fraîcheur (révisions), l'atomicité (CAS) ni l'idempotence, qui sont **backend**. Toute décision frontend est une **prévisualisation**, pas une autorisation : l'autorisation n'est valide qu'au point de linéarisation backend.
