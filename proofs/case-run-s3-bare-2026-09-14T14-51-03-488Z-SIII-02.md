# Mission « la bonne réponse dans le mauvais navigateur » — résolution

## Cadre et conventions

Je réponds **à partir des seuls contrats du dossier** (R01–R08, P01–P07). Les outils évoqués sont simulés : aucune action réelle sur des comptes, caches ou appareils n'est supposée. Je distingue systématiquement :

- **Établi** : conséquence logique directe d'un contrat.
- **Réfuté** : contredit par un contrat.
- **Non déterminé** : le dossier ne tranche pas.

Vocabulaire :
- **Divulgation** : octets d'un objet franchissant une frontière d'autorisation (R04 : « un octet émis est divulgué »).
- **Affichage erroné** : la vue courante présente un résultat d'un autre contexte (R07).
- **Mutation indûment autorisée** : écriture acceptée alors que le point de décision (R02) ne l'autorisait pas.

- P02, P03 = **divulgation** pure (octets franchis).

- P04 = **mutation indûment autorisée** + affichage erroné.

## Q2 — Condition nécessaire de partage de cache, analyse K-a…K-d, politique

### Condition nécessaire

Deux réponses peuvent partager une entrée de cache **seulement si** elles sont **substituables** : mêmes droits effectifs, même objet, même finalité, même révision de politique, même représentation. Formellement, si `D(r)` est la décision d'autorisation d'une réponse `r` (R02 : principal, organisation, objet, action, finalité, révision), alors :

> **Condition nécessaire** : `cache_key(r₁) = cache_key(r₂) ⇒ D(r₁) = D(r₂)` **et** `repr(r₁) = repr(r₂)`.

C'est une condition **nécessaire**, pas suffisante : elle n'empêche pas un cache de servir une entrée après révocation (R02 ne retire pas les octets déjà délivrés).

### Analyse des candidats

- **K-a = chemin.** Insuffisant : R01 dit que `dossier_id` n'est unique que dans une organisation ; `/dossiers/17` désigne SOLEIL/17 et LUNE/17. **Réfuté** comme clé de partage.
- **K-b = organisation + dossier.** Mieux : distingue les organisations. Mais R01 précise que le **même rôle nommé AGENT** peut avoir des permissions différentes selon la personne et le dossier. Deux principaux de la même organisation peuvent donc avoir des droits distincts sur le même objet. **Insuffisant** dès que les permissions individuelles diffèrent.
- **K-c = organisation + dossier + nom de rôle.** P05 le dit explicitement : « aucun nom de rôle ne garantit ici l'identité des projections autorisées ». **Réfuté** comme garantie.
- **K-d = contexte d'autorisation complet + révision des données + langue + version de représentation.** C'est le seul candidat qui satisfait la condition nécessaire : il capture `D(r)` et `repr(r)`. **Retenu.**

### Politique concrète pour les réponses protégées

1. **CDN** : ne pas mettre en cache les réponses protégées. R03 dit que le CDN n'utilise que `(chemin, langue)` et ignore Cookie/Vary — donc toute mise en cache y est structurellement dangereuse. Politique : `Cache-Control: private, no-store` sur tout objet protégé.
2. **Service worker** : clé = **K-d** (contexte d'autorisation complet + révision + langue + version de représentation), jamais le chemin seul. Purge à la déconnexion et à tout changement de contexte (R05 : les onglets ne se synchronisent pas instantanément → invalidation explicite).
3. **Cache mémoire frontend** : clé = **K-d**, pas `['dossier', dossier_id]` (R03 le dit insuffisant).

### Pourquoi une clé n'est pas un contrôle d'accès

Une clé de cache est un **index de stockage**, pas une **décision**. Elle ne fait qu'éviter les collisions ; elle ne vérifie ni le principal, ni la finalité, ni la révision de politique au moment du service. Un cache peut servir une entrée dont la clé est correcte mais dont la décision a été révoquée depuis (R02 : la révocation est une écriture sérialisée dans le domaine de décision, pas dans le cache). **La clé protège contre la confusion, pas contre la révocation.** Le contrôle d'accès reste au point de décision (R02), à chaque lecture ou mutation.

## Q3 — Machine d'état : changement de contexte, chargement, mutation

### États

- `CTX` : contexte courant `(principal, organisation, génération)`.
- `VIEW` : vue affichée `(génération, objet, état)`.
- `PENDING` : requêtes en vol `{id, génération_émise, type}`.
- `MUT` : mutations en vol `{id, génération_émise, organisation_cible}`.

### Invariants

- **I1** : `VIEW.génération = CTX.génération` (R07).
- **I2** : une réponse n'est appliquée que si `response.génération = CTX.génération` (R05).
- **I3** : une mutation n'est émise qu'avec l'organisation **du serveur**, jamais du JSON client (R06).
- **I4** : le rendu serveur ne diffuse aucun octet avant décision (R04).
- **I5** : toute annonce accessible nomme le contexte de l'opération (R07).

### Pseudo-code

```
# Changement de contexte
onChangeContext(nouveau):
    CTX.génération += 1
    CTX.organisation = nouveau
    invalider_cache_mémoire(K-d)          # R03
    invalider_service_worker(K-d)         # R03, R05
    VIEW = vide
    annoncer_accessible("Contexte " + nouveau + ", génération " + CTX.génération)

# Chargement
onLoad(dossier_id):
    g = CTX.génération
    PENDING.add({id, g, type: "read"})
    réponse = fetch(chemin, credentials, en-tête: {génération: g})
    onResponse(réponse):
        si réponse.génération != CTX.génération:      # I2
            journaliser("résultat ancien contexte " + réponse.génération)
            afficher_bandeau("Opération exécutée dans l'ancien contexte")
            return
        VIEW = réponse
        annoncer_accessible("Dossier " + réponse.organisation + "/" + réponse.dossier_id)

# Mutation
onMutate(dossier_id, payload):
    g = CTX.génération
    org = CTX.organisation                            # I3 : jamais depuis le JSON client
    MUT.add({id, g, org})
    réponse = fetch(mutation, en-tête: {génération: g, org: org, csrf: jeton})
    onMutationResponse(réponse):
        si réponse.génération != CTX.génération:      # R07
            afficher_bandeau("Mutation exécutée dans " + réponse.organisation
                             + " (ancien contexte)")
            # ne pas annoncer comme opération du contexte courant
        sinon:
            annoncer_accessible("Mise à jour réussie dans " + réponse.organisation)
```

### Rendu serveur (R04)

```
rendre(dossier):
    décision = décider(principal, org, objet, action, finalité, révision)   # R02
    si décision.refus:
        émettre(fragment_refus)          # aucun octet privé avant
        statut = 403
    sinon:
        émettre(fragment_contenu)        # nom + note privée
        statut = 200
```

**Invariant I4** : le fragment de contenu n'est émis **qu'après** décision favorable. P02 est réfuté par construction.

### Onglets (R05)

Chaque onglet a sa propre `CTX.génération`. Un changement de contexte dans un onglet **n'est pas** instantanément propagé. Donc :
- chaque onglet invalide ses propres caches (K-d) ;
- un canal `BroadcastChannel` (ou équivalent) propage la nouvelle génération **au mieux** ;
- en l'absence de propagation, I2 protège chaque onglet individuellement.

### Accessibilité

Toute transition annonce : contexte, génération, organisation de l'opération. R07 impose de **séparer** « opération exécutée dans l'ancien contexte » et « état affiché dans le contexte actuel ». Les annonces ne doivent jamais qualifier une opération SOLEIL de « LUNE ».

## Q4 — Ordre logique révocation / lecture / mutation ; réparation API ; mutation tardive

### Ordre logique

R02 : la révocation est une **écriture sérialisée** dans le domaine de décision. L'objectif normal interdit les lectures/mutations dont le **point de décision est postérieur** à la révocation. Donc :

> **Ordre** : `révocation < point_de_décision(lecture|mutation)` ⇒ refus.
> `point_de_décision < révocation` ⇒ autorisé, même si la réponse arrive après.

C'est exactement ce que R02 énonce : « il ne prétend pas retirer des octets déjà délivrés ni annuler une lecture autorisée avant la révocation mais reçue plus tard ».

### Réparation de l'API (R06)

L'API actuelle :
- extrait l'organisation d'un champ JSON → **faille** : le client choisit l'organisation.
- accepte `allowed=true` du frontend → **faille** : le client décide.
- jeton = identité seule → **insuffisant** : pas de preuve de finalité ni de révision.

Version corrigée :
1. **Session serveur** : l'organisation et le principal viennent de la session, jamais du corps JSON.
2. **Protection CSRF** : jeton anti-forgery lié à la session (les cookies sont envoyés automatiquement, R06).
3. **Validation atomique** : le point de décision (R02) lit principal, organisation, objet, action, finalité, révision **dans la même transaction** que la mutation.
4. **Révision de politique** : incluse dans la décision ; une révocation incrémente la révision.

### Mutation tardive (P04)

L'annulation navigateur est une **tentative de transport** (R05), sans garantie. Si le backend a déjà reçu la mutation :
- elle peut aboutir dans SOLEIL (autorisée avant révocation) ;
- le composant ne doit **pas** l'annoncer comme opération LUNE (R07).

Traitement :
- la réponse porte `organisation_cible` et `génération_émise` ;
- si `génération_émise != CTX.génération`, afficher « Mutation exécutée dans SOLEIL (ancien contexte) » ;
- ne jamais réécrire le JSON en transit pour remplacer SOLEIL par LUNE (P04 le propose : c'est **réfuté**, car cela falsifie l'origine de l'opération et viole R07).

## Q5 — Non-divulgation (R08), impossibilité de P06, garantie honnête

### Propriété de non-divulgation (périmètre R08)

**Énoncé** : dans le périmètre R08 (navigateur non hostile, canaux temporels et OS hors périmètre), aucune réponse servie à un principal `p` dans le contexte `c` ne contient d'octets d'un objet dont la décision `D` pour `p` dans `c` est un refus.

**Preuve (esquisse)** :
1. **Rendu** : par I4, le fragment de contenu n'est émis qu'après décision favorable (R04). Donc pas de fuite par le rendu.
2. **Cache** : par K-d, une entrée n'est servie que si le contexte d'autorisation complet correspond. Une entrée d'un autre contexte n'est pas substituable (Q2).
3. **Service worker** : purge à la déconnexion et au changement de contexte (Q3). P03 est réfuté par construction.
4. **API** : la décision est atomique (R02) et l'organisation vient de la session (R06). Pas de mutation cross-organisation.
5. **Erreurs** : R08 impose que les messages d'erreur n'exposent ni contenu ni existence d'un dossier d'une autre organisation. Donc les refus sont **indifférenciés** (même message pour « inexistant » et « non autorisé »).

**Limite explicite** : R08 dit que toute donnée déjà envoyée peut avoir été copiée. La propriété porte sur **ce qui est servi**, pas sur **ce qui a été reçu**. C'est pourquoi R02 ne prétend pas retirer les octets déjà délivrés.

### Impossibilité de P06

P06 promet : « suppression immédiate de toute copie, dans tous les onglets, tout cache et tout appareil hors ligne, sans perdre une seule mise à jour légitime ».

**Preuve d'impossibilité** :
- R08 : « aucun canal ne peut contacter un appareil isolé ». Un appareil hors ligne est, par définition, non joignable.
- R02 : la révocation n'annule pas les octets déjà délivrés.
- R05 : les onglets ne reçoivent pas instantanément tous les changements de session.
- Donc « immédiatement » et « tous les appareils » sont **contradictoires** avec R08. **P06 est réfuté.**

De plus, « sans perdre une seule mise à jour légitime » est contradictoire avec toute révocation qui invalide des mutations en vol (R02 : une mutation dont le point de décision est postérieur à la révocation est refusée).

### Garantie produit honnête

> « Une révocation empêche toute **nouvelle** lecture ou mutation dont le point de décision est postérieur à la révocation. Les octets déjà délivrés peuvent subsister sur un appareil isolé ; ils ne seront pas re-servis par nos caches ni par notre API. Les opérations déjà autorisées avant la révocation peuvent aboutir et sont présentées comme exécutées dans l'ancien contexte. »

Cette garantie est **bornée** : elle ne promet ni l'effacement des copies reçues, ni l'annulation des mutations déjà acceptées, ni la synchronisation instantanée des onglets.

## Q6 — Tests adversariaux et oracles

### Test 1 — Réponse tardive (P01)

- **Scénario** : session SOLEIL gén. 8, lecture `/dossiers/17` ; bascule LUNE gén. 9 ; charger LUNE/17 ; forcer l'arrivée de la réponse SOLEIL **après** la réponse LUNE.
- **Oracle** : la vue affiche LUNE/17 ; la réponse SOLEIL est journalisée comme « ancien contexte » et **ne remplace pas** la vue (I2, R07). Échec si `setDossier` écrase sans vérifier la génération.

### Test 2 — Fragment anticipé (P02)

- **Scénario** : requête sans permission ; capturer les octets émis.
- **Oracle** : aucun octet du nom ou de la note privée n'est émis avant le fragment de refus (I4, R04). Échec si le premier fragment contient des données privées, même masquées.

### Test 3 — Rejeu local (P03)

- **Scénario** : session SOLEIL met en cache SW ; déconnexion ; session LUNE demande le même chemin hors ligne.
- **Oracle** : le SW ne sert **pas** le JSON SOLEIL (purge à la déconnexion, clé K-d). Échec si le backend n'est pas contacté et que le JSON SOLEIL est renvoyé.

### Test 4 — Mutation tardive (P04)

- **Scénario** : gén. 8, mutation SOLEIL envoyée ; bascule LUNE gén. 9 ; le backend reçoit la mutation.
- **Oracle** : la mutation aboutit dans SOLEIL ; l'UI affiche « Mutation exécutée dans SOLEIL (ancien contexte) » et **non** « Mise à jour réussie » en LUNE (R07). Échec si le JSON en transit est réécrit SOLEIL→LUNE.

### Test 5 — Clé K-b vs permissions individuelles (exigé)

- **Scénario** : deux principaux `p₁`, `p₂` de la **même organisation** LUNE, même rôle nommé AGENT, mais permissions individuelles différentes sur LUNE/17 (R01 : « le même rôle nommé AGENT peut correspondre à des permissions différentes selon la personne et le dossier »). `p₁` a le droit de lire, `p₂` non.
- **Oracle avec K-b** (organisation + dossier) : le cache sert la même entrée à `p₁` et `p₂` → **fuite** vers `p₂`. Le test **passe** avec K-b (le cache est bien partagé) mais **échoue** au sens sécurité : `p₂` reçoit des octets non autorisés.
- **Oracle avec K-d** : les contextes d'autorisation diffèrent → entrées distinctes → `p₂` reçoit un refus. Le test **échoue** avec K-b et **passe** avec K-d.
- **Formulation** : « test qui passe avec K-b mais échoue avec des permissions individuelles différentes » = le test de partage réussit (même clé), mais l'assertion de non-divulgation échoue. C'est précisément la démonstration que K-b est insuffisant.

### Test 6 — Erreurs indifférenciées (R08)

- **Scénario** : demander un dossier inexistant dans LUNE et un dossier existant dans SOLEIL sans permission.
- **Oracle** : messages d'erreur **identiques** (ni contenu ni existence révélés). Échec si les messages diffèrent.

### Test 7 — Branche positive (P07)

- **Scénario** : agente LUNE habilitée lit puis modifie LUNE/17, politique stable.
- **Oracle** : lecture et mutation réussissent ; aucune sur-restriction. Échec si l'architecture masque tous les dossiers en permanence (interdit par P07).

## Synthèse : établi / réfuté / non déterminé

**Établi**
- P01 = affichage erroné (et divulgation potentielle) ; P02 = divulgation ; P03 = divulgation ; P04 = mutation indûment autorisée + affichage erroné.
- K-d est la seule clé satisfaisant la condition nécessaire de partage.
- Une clé n'est pas un contrôle d'accès.
- L'ordre logique est `révocation < point_de_décision ⇒ refus`.
- La non-divulgation tient dans le périmètre R08, sauf pour les octets déjà reçus.
- P06 est impossible.
- P07 doit rester possible.

**Réfuté**
- K-a, K-b, K-c comme clés de partage suffisantes.
- P06 comme promesse réalisable.
- La réécriture du JSON en transit (P04) comme correctif.
- Le 403 final de P02 comme annulation de la fuite.

**Non déterminé**
- Le mécanisme exact de propagation inter-onglets (R05 dit seulement « pas instantanément »).
- La durée de rétention des caches après révocation (R02 ne la fixe pas).
- Le format précis des messages d'erreur indifférenciés (R08 impose l'indifférenciation, pas la forme).

**Garantie produit finale** : révocation = blocage des **nouvelles** décisions postérieures ; les octets déjà délivrés et les mutations déjà autorisées ne sont pas annulés ; l'UI distingue explicitement l'ancien contexte du contexte courant ; aucune promesse d'effacement universel n'est tenable.
