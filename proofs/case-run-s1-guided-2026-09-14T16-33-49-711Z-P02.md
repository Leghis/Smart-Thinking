**Q1 — Graphe de conflits (22 arêtes orientées).** Règle : $T_i \to T_j$ si $T_i$ lit un registre que $T_j$ écrit, ou si $T_i$ écrit un registre que $T_j$ lit (écritures disjointes ⇒ aucune arête WW).

$$E=\{(1,2),(1,3),(1,6),(2,1),(2,3),(2,5),(2,6),(3,1),(3,2),(3,4),(3,5),(4,3),(4,5),(4,6),(5,2),(5,3),(5,4),(5,6),(6,1),(6,2),(6,4),(6,5)\}$$

Justification des orientations : $T_1$ lit $b$ (écrit par $T_2$) ⇒ $1\to2$ ; $T_1$ lit $f$ (écrit par $T_6$) ⇒ $1\to6$ ; $T_2$ lit $c$ (écrit par $T_3$) ⇒ $2\to3$ ; $T_3$ lit $a$ (écrit par $T_1$) ⇒ $3\to1$ ; etc. **L'historique n'est PAS sérialisable** : le cycle $T_1\to T_2\to T_3\to T_1$ existe (détecté par DFS).

**Q2 — Réparation optimale.** Coût minimal $=18$, **unique** : retirer $\{T_2,T_3,T_4,T_6\}$ ($4+6+3+5=18$). Ordres sériels de l'historique réparé ($T_1,T_5$ conservés) : **$T_1 \prec T_5$ ou $T_5 \prec T_1$** (2 ordres). Nombre minimal de retraits $=4$ (4 ensembles distincts de taille 4 : $\{1,2,4,5\},\{1,3,5,6\},\{2,3,4,6\},\{2,3,5,6\}$) — **distinct du coût minimal**.

**Q3.** Non : écritures disjointes + snapshot ne suffisent pas (write skew, cycle ci-dessus). Les horodatages de validation ne réparent pas (ils ordonnent les validations, pas les lectures).

**Q4.** Impossible avec le premier contrat (preuve par deux exécutions indiscernables).

**Q5.** Outbox transactionnelle + service idempotent par clé + rejeu.

**Q6.** Fencing ≠ idempotence ; clé sans liaison au contenu insuffisante.

## Preuves et certificats

- **Énumération exhaustive** (compute) : $2^6=64$ sous-ensembles testés ; aucun retrait de taille $\le 3$ n'est acyclique (minorant) ; seuls 4 ensembles de taille 4 le sont ; coût 18 atteint uniquement par $\{2,3,4,6\}$ ⇒ optimalité + unicité. Tri topologique exhaustif ⇒ exactement 2 ordres.
- **Q4 (indistinguabilité)** : Exécution A = `apply` envoyé, réponse perdue, rejeu → 2 effets. Exécution B = `apply` envoyé, panne avant journalisation, reprise rejoue → 2 effets. Même journal, même absence de réponse ⇒ indiscernables, mais nombre d'effets différent. Rejouer viole exactly-once ; ne pas rejouer viole l'exécution finale.
- **Q5** : frontière atomique = validation + insertion outbox dans la même transaction locale ; clé $k=\text{hash}(txid,\text{payload})$ ; dédup persistante côté service ; points de panne couverts (avant outbox → rollback ; après outbox avant envoi → rejeu ; après envoi avant marquage → rejeu dédupliqué ; après marquage → rien).
- **Q6** : contre-exemple fencing : $W_1$ envoie `apply(token=5)`, réponse perdue, rejoue `apply(token=5)` → 2 effets (le token n'empêche pas le doublon).

## Pièges traités

1. **Snapshot vs sérialisabilité** : ordre sérialisable explicite fourni ($T_1\prec T_5$ ou $T_5\prec T_1$) ; snapshot cohérent par transaction ≠ ordre global.
2. **Tous les sous-ensembles** : les 64 sous-ensembles énumérés, pas seulement les cycles courts.
3. **Effet externe irréversible** : un rollback ne l'annule pas ; d'où outbox + idempotence (Q5).
4. **Exactly-once / fencing / idempotence / autorisation** : distingués explicitement (Q4, Q6).

## Limites / impossibilités

- **Q4** : avec `apply` non idempotent, non transactionnel, sans lecture d'existence, aucun algorithme ne garantit exactly-once **et** exécution finale (dilemme sûreté/vivacité).
- **Q3** : les horodatages ne peuvent pas réparer un historique dont les lectures sont déjà fausses.
- **Q5** : la garantie exige que le service externe accepte une clé d'idempotence et une dédup persistante ; sans cette modification du contrat, l'impossibilité de Q4 subsiste. La réparation logique (Q2) est un audit, elle n'annule pas rétroactivement un effet externe.
